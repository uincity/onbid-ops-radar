# 홈페이지 모니터링 사전 조사 (M0) — 2026-11-04

- 상위 문서: [plan-homepage-monitoring.md](plan-homepage-monitoring.md) M0 (W00-1~W00-3), [prd-homepage-monitoring.md](prd-homepage-monitoring.md) §6.3·§12
- 조사 방법: 읽기 전용 GET만 사용(로그인·폼 제출·쓰기 없음). 사용자 PC에서 `curl`(User-Agent `OnBidOpsRadar-Monitor/1.0`) 5번, 앱 내장 브라우저로 메인 화면 1번 열기(네트워크 요청 목록 확인), Node `tls`로 인증서 확인 1번.
- 조사한 시각: 2026-11-04 오후(KST). 이 값들은 **그날의 관측**이며, 표식은 첫 1주 관찰로 다시 확인합니다.
- 한계: 사용자 PC(일반 인터넷망)에서 한 결과입니다. **Vercel 서울 리전에서도 같은지는 아직 확인하지 못했습니다(W00-1 미완료).**

## 1. 요약 (계획에 영향을 주는 것)

1. `https://www.onbid.co.kr/`는 **781바이트 이동 스텁**입니다. 실제 화면은 `https://www.onbid.co.kr/op/meminf/lgnmng/prtllgn/PrtlLgnController/main.do`입니다.
2. 실제 메인 화면은 **서버가 HTML을 만들어 주는 방식**이고(약 609KB, 본문 글자 약 3,000자), 같은 요청을 3번 해도 크기·본문이 **완전히 같았습니다.** 그래서 내용 표식(L3)은 헤드리스 브라우저 없이 가능합니다.
3. 메인 화면을 실제 브라우저로 열어도 **데이터를 가져오는 별도 요청(XHR/fetch, JSON)은 없었습니다.** PRD가 가정한 "L4 기능 점검 = 데이터 요청 1~3개 호출"은 **대상이 없습니다.** 대신 홈페이지가 의존하는 **파일 서버 요청(`dnldImgFile.do` 썸네일 이미지 16개)** 과 **대기열 서비스(`wait.onbid.co.kr`)** 가 백엔드 의존의 확인 지점입니다.
4. 메인 HTML 본문에는 **날짜·가격이 없습니다**(메뉴와 이미지 위주). PRD의 L5(최신 공고 날짜로 신선도 확인)를 **HTML에서는 할 수 없습니다.** 신선도는 이미 매일 점검하는 OpenAPI(공고 목록 등)의 최신 일시로 대신하는 안을 제안합니다.

## 3. 제안 값 (M1에서 `web-targets.json`에 넣을 초안)

### 3.1 점검 구성

| 층 | 대상 | 제안 |
|---|---|---|
| L1 | `www.onbid.co.kr:443` | DNS, TCP/TLS 연결, 인증서 만료·호스트명, 남은 일수 |
| L2 | `main.do` | 상태 코드, 총 응답 시간, 리다이렉트 추적, 최종 주소. 저하 기준 3,000ms(정상 1.1~1.3초라 여유 있음. 첫 주 관찰 뒤 확정) |
| L2 보조 | `/`(스텁) | 이동 코드(`location.replace`)와 이동 대상이 `main.do`인지. 스텁이 바뀌면 **검증 불가**(실패 아님) |
| L2 보조 | `wait.onbid.co.kr` 설정 파일 | 200과 JSON 형식. 홈페이지 본체 판정과 **분리해 기록**(첫 주 관찰 뒤 대표 판정 반영 여부 결정) |
| L3 | `main.do` 본문 | 아래 3.2 |
| L4 | 홈페이지의 썸네일 이미지 1개 | HTML에서 `dnldImgFile.do` 주소 1개를 뽑아 GET: 200, 이미지 `Content-Type`, 크기 하한. 파일 서버 의존을 확인. 주소의 `atchFileLstNo`는 바뀌므로 매번 HTML에서 새로 뽑습니다 |
| L5 | (HTML에서는 불가) | OpenAPI(이미 점검 중인 공고 목록 등)의 최신 일시를 재사용하는 안. 별도 호출 없음 |

### 3.2 L3 내용 표식 초안

관측한 3회 표본에서 모두 안정적이었던 것만 제안합니다.

- `must_contain`(모두 있어야 함): 제목 `<title>온비드</title>`, 메뉴 낱말 `물건검색`, `공고검색`, `이용안내`, `로그인`, 그리고 자체 스크립트 `/js/op_main.js`.
- `must_not_contain`: 점검 안내는 `점검`이라는 낱말이 평소에는 없으므로 `시스템 점검`, `서비스 점검`, `점검 중`, `일시 중단`, `이용이 불가` 같은 **구**로 찾습니다. 차단 페이지 문구는 평소에도 나오는 `차단` 낱말 하나가 아니라 `Access Denied`, `Forbidden`, `Request blocked` 같은 **구체적인 문구**로 찾고, 걸리면 **검증 불가**로 분리합니다. 실제 점검 안내 페이지가 어떻게 생겼는지는 아직 본 적이 없어서, 공지 사례로 보강해야 합니다(§5 열린 질문).
- `min_bytes`: 관측 크기 609,185바이트. 하한은 **300,000바이트**(약 절반, 일부만 오는 응답이나 오류 페이지를 거름)로 제안하고 첫 주 관찰로 조정합니다.
- JS 번들 확인: `op_main.js`(5KB)와 `component.js` 중 1~2개를 GET해 200과 크기를 봅니다. 번들 주소에 붙는 `?version=` 값은 배포마다 바뀌므로 **HTML에서 뽑아** 씁니다.

## 5. 아직 모르는 것

1. **Vercel 서울 리전에서의 접속 결과(W00-1).** 해외 IP·WAF 차단은 확인되지 않았습니다. 사용자 PC에서는 차단이 없었습니다. 임시 확인 경로를 만들려면 배포가 필요해서, M1의 입구 경로(W07)를 처음 배포할 때 함께 확인하는 것이 가장 가볍습니다.
2. **실제 점검 안내 페이지의 모양.** 온비드가 정기 점검을 할 때 홈페이지가 어떻게 보이는지 본 적이 없습니다. 공지사항(온비드 공지)이나 과거 점검 안내 화면 캡처가 있으면 `must_not_contain`을 보강할 수 있습니다. 담당 부서에서 점검 안내 화면의 예(문구·HTTP 상태)를 알려 주시면 가장 정확합니다.
3. **로그인 후 화면, 입찰 등 기능 동작**은 범위 밖입니다(PRD 비목표).
4. **하루 중 시간대별 변동.** 지금은 낮 시간대 한 번의 관측입니다. 야간·주말·입찰 마감 시간대의 응답 시간과 크기는 첫 주 관찰로 확인합니다.
