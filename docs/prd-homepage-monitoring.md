## 0. Claude Code 작업 지침 (먼저 읽을 것)

이 문서는 기존 OnBid Ops Radar 저장소에 기능을 **추가**하기 위한 PRD다. 새 서비스를 만들지 않는다.

1. 구현 전에 기존 코드에서 아래를 먼저 찾아 읽고, 그 패턴을 그대로 따른다.
   - 서비스 등록부 (docs/api-registry.md 및 등록부를 담은 코드/테이블)
   - 6가지 판정 로직 (정상(데이터) / 정상(무데이터) / 저하 / 실패 / 검증 불가 / 미점검)
   - 이상징후 생성 및 중복 제거 로직
   - Supabase 스케줄러(pg_cron 등) 설정과 08:30 실행 여부 확인 로직
   - 설정값을 한곳에서 관리하는 모듈
2. 기존 판정 체계와 테이블을 **확장**한다. 같은 목적의 새 체계를 따로 만들지 않는다.
3. 기능마다 단위·DB·화면 시험을 함께 작성한다 (기존 방식: 단위 / DB(RLS 포함) / 화면).
4. 온비드에 보내는 요청은 **읽기 전용 GET만** 허용한다. 로그인, 폼 제출, 쓰기 요청은 금지.
5. 비밀값(텔레그램 봇 토큰 등)은 서버 환경변수/Supabase secrets에만 둔다. 브라우저 번들, 로그, DB 평문, 커밋에 넣지 않는다.
6. 마일스톤(§12) 순서대로 진행하고, 각 단계가 끝나면 수용 기준(§11)으로 검증한 뒤 다음 단계로 넘어간다.
7. 이 문서와 기존 코드가 충돌하면 임의로 정하지 말고 충돌 내용을 보고한다.

## 1. 배경

- 현재 OnBid Ops Radar는 온비드 OpenAPI 26종(오퍼레이션 29개)을 **매일 08:00에 1회** 점검한다.
- 온비드 **홈페이지(https://www.onbid.co.kr/)** 자체의 가용성은 점검하지 않는다. 일과 중에 장애가 나면 다음 날 점검 때까지, 또는 이용자 문의가 올 때까지 알 수 없다.
- 결과는 대시보드에서만 볼 수 있다. 담당자가 화면을 열지 않으면 이상을 알 수 없다 (푸시 알림 없음).
- 사전 관찰(2026-11-04, [조사 결과](web-monitor-research.md)): `https://www.onbid.co.kr/`는 781바이트짜리 **자바스크립트 이동 스텁**(대기열 에이전트 로드 + `main.do`로 이동)이다. 실제 화면 `…/PrtlLgnController/main.do`는 서버가 HTML을 만들어 주는 약 609KB 문서이고 같은 요청에 항상 같은 결과가 왔다. 스텁만 보면 실제 화면이 죽어도 HTTP 200이 나오므로 **HTTP 200만으로는 정상 판정을 할 수 없고, 점검은 `main.do` 기준으로 해야 한다.**

## 2. 목표 / 비목표

### 목표
- G1. 온비드 홈페이지를 **1시간 간격**(설정 가능)으로 외부 이용자 관점에서 점검한다.
- G2. 접속 → HTTP → 내용 → 기능(파일 서버) → 신선도의 층별 점검으로 "껍데기만 뜨는 장애"까지 잡는다.
- G3. 상태가 바뀌면(정상→실패, 실패→정상) **텔레그램으로 알림**을 보낸다. 채널은 교체할 수 있게 만든다.
- G4. 알림과 동시에 기존 이상징후로 등록해 배정·조치·이력 흐름을 그대로 쓴다.
- G5. 모니터 자체가 멈추면 이를 감지해 알린다 (dead-man switch).

### 비목표
- 온비드 내부 서버 지표(CPU, DB, 전체 이용자 성공률) 수집. 외부 관측만 한다.
- 로그인이 필요한 화면, 입찰 등 쓰기 동작의 점검.
- 다지점(여러 지역/통신사) 관측. 1차 범위는 단일 관측 지점.
- 기존 API 일일 점검의 주기 변경 (08:00 1회 유지).

## 3. 용어

| 용어 | 정의 |
|---|---|
| 점검 대상(target) | **웹 등록부(`data/registry/web-targets.json`)** 의 한 항목. 기존 API 서비스 등록부와 별개의 파일이며, 초기 대상은 `onbid-home` 하나 |
| 프로브(probe) | 한 대상에 대한 한 층의 점검 단위 (예: tls, http, content) |
| 점검 실행(run) | 스케줄 1회분. 여러 대상·프로브를 포함 |
| 확인 재시도(confirm retry) | 실패 시 짧은 간격을 두고 한 번 더 확인하는 것 |
| 정상 계열 | **정상(데이터), 정상(무데이터)**. 저하는 정상 계열이 아니다 |
| 실패 계열 | 실패(확정 실패 포함). 저하·검증 불가·미점검은 실패 계열이 아니다 |
| 상태 전환 | 대상의 대표 판정이 정상 계열 ↔ 실패 계열(또는 저하)로 바뀌는 것. 전환표는 FR-6 |
| 대표 판정 | L1(인증서 임박 제외)·L2·L3(·M3의 L4)의 가장 나쁜 판정. **보조 프로브와 인증서 임박 신호는 포함하지 않는다** (FR-3) |
| 사건(incident) | 대상 하나가 **확정 실패이거나, 저하 알림이 확정된 시점부터** 정상 계열로 돌아올 때까지의 구간. 저하가 1회만 있다가 알림 전에 정상으로 돌아오면 사건이 아니다. 사건 번호 `incident_no`(대상별로 사건이 시작될 때마다 1씩 증가)가 알림 멱등 키에 쓰인다. 이상징후는 보통 **WEB_AVAILABILITY 1건과 1:1**이지만 담당자가 사건 중간에 이상징후를 닫으면 같은 사건에서 새 이상징후가 만들어질 수 있고, 링크·복구 기록은 현재 열린 이상징후에 붙는다. 이상징후를 만들지 않는 알림(인증서 등)은 사건이 없다 |
| 일시 실패(flap) | 정시 점검이 실패였으나 확인 재시도에서 정상이 되어 확정되지 않은 실패. 결과 행의 표시 칸(`flap=true`)으로 남기며 7번째 판정이 아니다 |
| 계획 점검 창(maintenance window) | 온비드가 예고한 점검 시간. 이 시간의 실패는 알림·가용률에서 제외 |

## 4. 사용자

- 팀장 1명, 운영 담당자 1명 (기존 계정과 동일).
- 알림 수신: 위 2명의 텔레그램 (개인 chat 또는 그룹 chat 1개).

## 5. 기능 요구사항

### FR-1. 점검 대상 등록
- 웹 대상 등록부 `data/registry/web-targets.json`을 새로 만든다(Zod로 검증, 기존 API 등록부와 같은 방식). 기존 API 등록부(`api-registry.json`)와 DB는 바꾸지 않는다. DB에는 대상 키(문자열)만 둔다.
- 초기 대상: `onbid-home`. 구성은 **진입 스텁 `https://www.onbid.co.kr/`(보조 확인)** 와 **실제 화면 `https://www.onbid.co.kr/op/meminf/lgnmng/prtllgn/PrtlLgnController/main.do`(판정 기준)** 이다.
- 대상별 설정: 점검 주기, 타임아웃, 활성 여부, 프로브 목록, 내용 표식(§6.3: `must_contain`·`min_bytes`·`maintenance_phrases`·`block_phrases`·`maintenance_url_patterns`), 알림 여부.
- 요청마다 **https와 허용 호스트(`www.onbid.co.kr`, `wait.onbid.co.kr`)만** 허용한다. 리다이렉트·HTML에서 뽑은 주소가 허용 호스트 밖이면 요청하지 않고 `검증 불가`로 판정한다.

### FR-2. 층별 프로브 (§6 상세)
- L1 접속: DNS 조회, TCP/TLS 연결, 인증서 만료까지 남은 일수.
- L2 HTTP: 상태 코드, 총 응답 시간, 리다이렉트 체인, 최종 URL. 대상은 `main.do`. **보조 확인**: 진입 스텁 `/`(이동 코드와 이동 대상 확인), 대기열 서비스 설정 파일(`wait.onbid.co.kr/.../nf-setting.json`).
- L3 내용: 필수 표식 존재, 점검 안내 문구 부재, 응답 크기 하한, JS 번들 1~2개 확인.
- L4 기능(**v0.2 변경**): 메인 화면에는 데이터를 가져오는 XHR/fetch 요청이 **없다**(조사 §2.3). 대신 홈페이지 HTML에서 **파일 서버 썸네일 이미지 주소(`dnldImgFile.do`) 1개**를 매번 뽑아 GET해, 200·이미지 `Content-Type`·크기 하한을 확인한다. 주소 모양이 바뀌면 `검증 불가`.
- L5 신선도(**v0.2 변경**): 홈페이지 HTML에는 날짜가 없다. **이미 수집 중인 OpenAPI 공고 목록 결과(`collected_items`의 PUBLIC 목록)에서 최신 입찰 시작일시**를 읽어 영업일 기준으로 판단한다. 새 외부 호출 없음.
- 1차 구현(M1)은 L1~L3와 보조 확인, L4·L5는 M3.

### FR-3. 판정
- 프로브별로 기존 6가지 판정 중 하나를 낸다.
- 대상의 대표 판정 = **대표 판정에 포함되는** 프로브 중 가장 나쁜 판정 (우선순위 §6.6).
- 대표 판정에서 **제외**하는 것: ① 인증서 만료 임박 신호(L1 저하) ② 보조 확인(진입 스텁, 대기열 서비스). 이들은 결과를 기록하고 대시보드에 표시하되 **별도 알림**으로만 다룬다(FR-6). 제외하지 않으면 인증서 만료 14일 전부터 2주간 대표 판정이 계속 "저하"가 되어 매시간 저하 알림·이상징후가 나오고 진짜 성능 저하를 가린다.
- 판정 규칙은 결정적이어야 한다 (같은 입력 → 같은 판정).

### FR-4. 확인 재시도
- 대표 판정이 `실패`이고 **그 대상에 열린 사건이 없을 때만** `CONFIRM_RETRY_DELAY_SEC`(기본 90초, 실제 90~150초) 뒤 같은 대상을 1회 재점검한다. 이미 사건이 열려 있으면(장애 지속 중) 재시도하지 않는다.
- 재점검 결과별 처리:

| 재점검 결과 | 처리 |
|---|---|
| 실패 | **확정 실패**로 기록. 알림·이상징후 대상 |
| 정상(데이터/무데이터) | 일시 실패(flap)로 기록, 알림·이상징후 없음. 이 시점의 현재 상태는 정상 |
| 저하 | 확정 실패가 아님. 현재 상태를 저하로 두고 저하 규칙(FR-6)을 적용, flap 표시 |
| 검증 불가·미점검 | 확정 실패가 아님. 현재 상태를 해당 값으로 두고 FR-6의 검증 불가 연속 규칙을 적용, flap 표시 |

- **복구 판정은 비대칭**이다: 열린 사건이 있을 때 정시 점검이 정상 계열이면 확인 없이 1회로 복구로 판정한다(복구 지연이 더 해롭다고 보기 때문. 복구가 곧 다시 실패하는 진동은 FR-12의 알림 상한으로 막는다).
- 재점검과 수동 점검도 웹 점검 실행 자리(동시 실행 1개)를 쓴다. 자리가 차 있으면 재점검은 다음 분에 다시 시도한다.

### FR-5. 스케줄
- 기존 Supabase 스케줄러에 매시간 작업을 추가한다. 기본은 매시 정각이 아닌 `:07`분 (설정 가능).
- 매시간 작업은 `web` 대상만 돈다. `api` 일일 점검과 서로 독립적이다.
- 실행 시간 상한을 지킨다. 웹 점검 전체의 시간 예산은 웹 전용 설정(`web_run_time_limit_seconds`, 기본 60초)으로 두고, 요청 타임아웃은 남은 예산보다 길게 쓰지 않는다(남은 예산이 없으면 나머지는 `미점검`). 기존 API 점검의 실행시간 설정(`run_time_limit_seconds`, 운영 80초)과 **섞지 않는다**. 점검 경로의 최대 실행시간(`maxDuration`)은 현재 90초다.

### FR-6. 알림
- 알림은 **상태 전환 시에만** 보낸다. 전환표(상태 → 상태, **확정 판정 기준**):

| 이전 → 이후 | 알림 |
|---|---|
| 정상 계열 → 확정 실패 | `🔴 장애 감지` (사건 시작, 이상징후 생성) |
| 정상 계열 → 저하 (연속 `DEGRADED_ALERT_COUNT`회째) | `🟠 성능 저하` (**이 시점에 사건이 시작**되고 이상징후가 생긴다. 그 전에는 알림도 사건도 없음) |
| 저하 → 확정 실패 | `🔴 장애 감지` |
| 확정 실패 → 저하 | 알림 없음(사건 유지). 사건은 정상 계열이 될 때 닫힌다 |
| 확정 실패/저하 → 정상 계열 | `🟢 복구` (지속 시간 포함). 저하만 있었고 알림을 보낸 적이 없으면 복구 알림 없음 |
| 그 외(같은 계열 유지, 검증 불가·미점검 구간 포함) | 알림 없음 |

- 실패가 이어지면 `REALERT_AFTER_HOURS`(기본 3시간)마다 `⏳ 장애 지속` 알림 1회. **기준 시각은 그 사건의 마지막 알림(장애 감지 또는 직전 지속 알림) 시각**이고, 점검 시각마다 `경과 ≥ N시간`이면 발송한다(정시 점검이 1시간 간격이라 발송은 최대 1시간 늦을 수 있다). 경계: 2시간 59분은 미발송, 3시간 00분은 발송.
- **인증서 임박**(`CERT_WARN_DAYS`, 기본 14일, 남은 일수 ≤ 14): 대표 판정과 무관하게 **하루 1회** `🟡 인증서 만료 임박`. 이상징후는 만들지 않는다.
- **보조 확인 이상**(진입 스텁·대기열 서비스): 연속 `AUX_ALERT_COUNT`(기본 3회) 실패/검증 불가이면 `🟡 보조 점검 이상` 1회, 정상으로 돌아오면 해제 알림 없이 기록만. 대표 판정에는 반영하지 않는다(1주 관찰 뒤 조정).
- `검증 불가` / `미점검`은 즉시 알림하지 않는다. 같은 대상에서 연속 `UNVERIFIABLE_ALERT_COUNT`(기본 3회)가 되면 `⚪ 점검 불가 지속` 알림.
- 알림 채널은 인터페이스(`Notifier`)로 분리하고 1차 구현체는 `TelegramNotifier`.
- 알림 발송 결과(성공/실패, 응답 코드)는 **시도마다 한 줄씩 추가 기록**한다. 발송 실패는 최대 3회 재시도하고, 그래도 실패하면 대시보드에 표시한다.
- **멱등 키**: 같은 사건에 대한 중복 발송을 막되 **반복 알림이 막히지 않게** 사건 종류별로 키를 만든다.
  - 장애 감지·성능 저하·복구: `down:{incident_no}`, `degraded:{incident_no}`, `recovered:{incident_no}`
  - 장애 지속: `ongoing:{incident_no}:{n}` (n = 몇 번째 지속 알림)
  - 인증서 임박: `cert:{target}:{KST 날짜}`
  - 점검 불가 지속: `unverifiable:{연속 시작 실행 id}`
  - 모니터 정지: `stale:{마지막 정상 실행 id}:{n}`
  - 미등록 점검: `unplanned:{target}:{감지 시작 실행 id}`
  - 보조 점검 이상: `aux:{target}:{프로브}:{연속 시작 실행 id}`
  - 알림 억제 안내: `suppressed:{target}:{KST 날짜}`
  - 모니터 재개: `resumed:{정지 알림의 마지막 정상 실행 id}`
  - **키 선점은 한 곳에서만** 한다: 상태 전환에서 나온 알림은 상태 저장과 **같은 트랜잭션에서 키를 선점하고 `queued` 줄을 만든다.** 앱은 그 줄을 보고 발송하고 결과를 시도마다 한 줄씩 추가한다. 선점 뒤 앱이 죽어 발송하지 못한 알림은 매분 작업이 15분 뒤 다시 보낸다(유실 방지). 감시 함수가 보내는 알림(모니터 정지·재개)만 별도로 키를 선점한다.

### FR-7. 이상징후 연동
- **사건이 시작될 때**(확정 실패, 또는 저하 알림이 확정될 때) 기존 이상징후를 생성한다 (규칙 ID: **`WEB_AVAILABILITY`**, 기존 규칙 ID 관례를 따른 대문자 이름. 대상 키 `onbid-home`을 `item_key`로 쓴다).
- 같은 대상의 열린 이상징후가 있으면 새로 만들지 않고 발생 기록만 추가한다 (기존 중복 제거 규칙). 담당자가 사건 도중에 이상징후를 닫으면 다음 점검에서 새 이상징후가 만들어지고, 이후 알림 링크와 '복구 확인됨' 기록은 **현재 열린 이상징후**에 붙인다(닫힌 건에는 남기지 않는다).
- **오탐으로 종결한 건이 실제 장애를 숨기지 않게** 새 사건마다 다른 근거 해시(사건 시작 시각 포함)를 쓴다 — 기존 "정상 판정 건과 같은 값이면 새 건을 만들지 않는" 억제가 새 장애에 적용되지 않게 하기 위함이다.
- 복구되면 자동으로 종결하지 않는다. 이상징후 이력에 **`복구 확인됨` 사건을 추가**하고(상태는 바꾸지 않음), 종결은 담당자가 한다 (기존 처리 흐름 유지).
- 알림 메시지에 이상징후 상세 화면 링크(`/anomalies/{id}`)를 넣는다.
- **출처는 `WEB`을 새로 만든다**(확정, 2026-11-04 사용자 결정). 홈페이지 이상징후는 `source='WEB'`이고 OpenAPI의 `PUBLIC`과 집계가 섞이지 않는다. 바뀌는 곳: 이상징후 테이블의 출처 허용 값(DB 제약), 이상징후 목록 필터·출처 배지·대시보드 출처별 건수(`DEMO`는 계속 숨기고 `PUBLIC`·`WEB`을 보임), 이상징후 목록 검색 조건. **바뀌지 않는 곳**: 점검 실행·판정·수집 테이블(웹은 `web_*` 테이블이라 출처 값을 쓰지 않음), 설정값 `scheduled_source`(`DEMO`·`PUBLIC`만), 보고서 테이블의 출처 값(홈페이지 절은 `PUBLIC` 보고서 안에서 `WEB` 이상징후를 따로 다룬다). 기존 PUBLIC 보고서의 이상징후 표에는 `WEB` 이상징후를 섞지 않는다.

### FR-8. 모니터 자체 감시 (dead-man switch)
- `HEARTBEAT_STALE_MIN`(기본 130분) 동안 **정시 점검·재확인으로 정상 종료(`succeeded`·`partial`)한** 실행이 없으면 `⚫ 모니터 정지` 알림을 보낸다. **수동 점검과 시험 실행, 차단·실패한 실행은 세지 않는다**(cron이 죽었는데 수동 점검으로 감시가 리셋되는 일을 막는다). 기준 시각은 `max(마지막 정상 실행 종료, 점검을 다시 켠 시각)`이라 꺼 두었다가 켠 직후에는 정지 알림이 나가지 않는다.
- 감시 주체는 매시간 점검과 다른 실행 경로여야 한다: **별도 `pg_cron` 작업(기본 10분마다)** 이 DB 함수를 실행하고, 그 함수가 Vault의 비밀값과 `pg_net`으로 텔레그램을 **앱을 거치지 않고** 직접 호출한다. 점검 함수·앱이 죽어도 감시가 돈다.
- 정지가 이어지면 `HEARTBEAT_REALERT_HOURS`(기본 24시간)마다 재알림하고, 실행이 다시 정상 종료되면 `🟢 모니터 재개` 알림을 1회 보낸다.
- 기존 08:30 일일 점검 실행 확인은 `run_logs`에 **기록만** 하고 외부 알림은 보내지 않는다. 이 감시는 "DB 함수를 별도 `pg_cron`으로 실행한다"는 구조만 같고 **알림 발송은 새로 만든다.**
- `pg_net`은 비동기라서 호출 직후에는 발송 결과를 알 수 없다. 감시 알림은 **호출 때 `queued`로 기록하고, 다음 감시 주기(10분 뒤)에 응답을 읽어 `sent`/`failed`를 기록하며 실패하면 재발송(최대 3회)**한다. 그래서 감시 알림의 재시도 간격은 10분이다.
- 확인 필요: 텔레그램 주소에 봇 토큰이 포함되므로 `pg_net`의 요청 기록 테이블에 토큰이 남는지(남으면 즉시 지운다. 토큰이 주소 경로에 들어가므로 헤더 방식으로 바꾸는 것은 어렵다), 쓰는 `pg_net` 버전의 응답 테이블 이름·보존 시간.

### FR-9. 계획 점검 창
- **팀장만** 점검 창(시작~종료, 사유)을 등록·취소할 수 있다. 화면은 "홈페이지 모니터링" 화면(`/web`)에 둔다(§FR-10). 시간은 KST로 입력하고 **서버 액션이 `+09:00`을 붙여 한 번만 변환**한다. **창은 대상 하나를 반드시 지정한다**(전체 대상 창은 없음). 같은 대상의 창은 시간이 겹칠 수 없고, 길이는 최대 `WEB_WINDOW_MAX_HOURS`(기본 168시간)다. 창의 경계는 점검의 `started_at`이 `[시작, 종료)` 안이면 창 안으로 본다.
- 창 안의 결과는 판정은 그대로 기록하되 `planned_maintenance=true`(7번째 판정이 아니라 표시 칸)로 남기고 **알림·가용률 계산·이상징후 생성에서 제외**한다.
- 점검 안내 문구(`maintenance_phrases`)나 점검 안내 경로(`maintenance_url_patterns`)가 감지되면 **원판정은 `실패`(사유 `MAINTENANCE_DETECTED`)** 로 기록한다. 등록된 창 안이면 위처럼 제외하고, **창이 없으면** 장애 알림 대신 `🔧 미등록 점검 감지` 알림을 1회 보내며(이상징후는 만들지 않음) 그 구간은 가용률 분모에서 제외하고 "미등록 점검"으로 표시한다.
- 창이 끝났는데도 점검 문구가 계속되면 일반 실패로 처리한다. **창이 없는 점검 문구가 `WEB_UNPLANNED_ESCALATE_HOURS`(기본 6시간) 넘게 이어지면 일반 확정 실패로 승격**해 장애 알림을 보낸다(미등록 점검 알림만 영영 나가는 일을 막는다). 점검 문구가 감지되면 재확인은 하지 않는다. 사건이 열려 있는 중에 창이 시작되면 지속 알림은 보내지 않고, 복구는 창 안에서도 판정대로 처리해 복구 알림을 보낸다.
- **창 취소:** 시작 전 창은 취소 표시만 남기고(판정에서 제외), 진행 중 창은 종료 시각을 지금으로 당긴다. 이미 끝난 창은 취소할 수 없다.

### FR-10. 대시보드/보고서
- 화면: **"홈페이지 모니터링" 메뉴(`/web`)** 를 새로 둔다(로그인한 팀 계정 조회, 계획 점검 창·수동 점검은 팀장만). 내용: 현재 상태, 최근 24시간 판정 스트립, 점검 실행 이력, 알림 발송 기록(실패 표시 포함), 계획 점검 창.
- 대시보드에 "홈페이지" 카드: 현재 상태, 최근 24시간 시간대별 판정 스트립, 최근 응답 시간, 인증서 남은 일수. 카드는 `/web`으로 연결한다.
- 일일 점검보고서(출처 PUBLIC 보고서)에 홈페이지 절을 추가한다: 24회 중 판정 분포, 확정 장애 건수와 총 지속 시간, 일시 실패 횟수, 평균/최대 응답 시간.
- **판정 횟수의 정의**: 정시 점검(매시 :07)의 **확정 판정**을 센다(재시도로 정상이 된 경우 정상 1회 + 일시 실패 1회를 따로 표시). 수동 점검·재시도 실행 자체는 횟수와 가용률에서 제외한다.
- 가용률은 `정상 계열 / (판정 횟수 − 검증 불가 − 미점검 − 계획 점검 − 미등록 점검)`. 화면에 "단일 지점, 1시간 간격 외부 관측"이라고 명시한다.

### FR-11. 수동 점검
- "홈페이지 모니터링" 화면(`/web`)의 팀장용 즉시 점검 버튼. **수동 점검은 알림을 보내지 않는다**(보낼 상태 전환이 없다).
- **수동 점검은 대상의 현재 상태(`web_target_state`)·사건·알림·재시도 예약을 바꾸지 않는다.** 결과는 기록만 하고 "수동 점검" 표시를 붙인다. (상태를 바꾸면 복구 알림이 알림 없이 사라질 수 있다.)

### FR-12. 비활성화·알림 폭주 방지·롤백
- 즉시 끄는 장치: 설정 `web_monitor_enabled`(기본 true)를 false로 하면 점검·재시도·알림을 모두 멈춘다(자체 감시는 "의도된 정지"를 알림하지 않는다). 스케줄러 등록 스크립트는 웹 작업만 해제하는 옵션을 둔다.
- 알림 폭주 방지: 대상별 하루 알림 상한 `WEB_ALERT_DAILY_CAP`(기본 12건)을 넘으면 이후 알림은 기록만 하고 "알림 억제" 1건을 보낸다(모니터 정지 알림은 상한 밖).
- 롤백: 새 DB 객체는 마이그레이션 파일로만 만들고, 끄기(위)만으로 기존 API 점검에 영향이 없어야 한다. 운영 문서에 되돌리는 절차를 쓴다.

## 6. 판정 규칙 상세

모든 임계값은 설정 모듈에서 관리한다. 아래 값은 기본값이며 첫 1주 관찰 뒤 조정한다.

### 6.1 L1 접속
| 조건 | 판정 |
|---|---|
| DNS 실패, TCP 연결 실패, TLS 핸드셰이크 실패 | 실패 |
| 인증서 만료됨 / 호스트명 불일치 | 실패 |
| 인증서 만료까지 남은 일수 ≤ `CERT_WARN_DAYS`(14) | **인증서 임박 신호**(저하로 기록하되 **대표 판정에서 제외**, 별도 알림 — FR-3·FR-6) |
| 그 외 | 정상(데이터) |

남은 일수 = `floor((만료 시각 − 현재) / 24시간)`. 14일 0시간은 14일(임박), 15일은 임박 아님. 시험 경계: 14일/15일.

### 6.2 L2 HTTP
| 조건 | 판정 |
|---|---|
| 타임아웃 (`HTTP_TIMEOUT_MS` 기본 10000) | 실패 |
| 5xx | 실패 |
| 401·403·429 | 검증 불가. 차단/제한 가능성이 있으므로 실패로 세지 않음. 연속이면 FR-6 규칙으로 알림 |
| 404·410 (**결정 필요**, 기본안) | **실패**. 메인 화면 주소가 사라진 것은 장애일 수 있다. 판정은 `main.do` 기준이며 스텁 `/`의 404는 검증 불가 |
| 그 밖의 4xx | 검증 불가 |
| 리다이렉트 10회 초과 | 실패 |
| 최종 URL이 `maintenance_url_patterns`와 일치 | 원판정 `실패`(사유 `MAINTENANCE_DETECTED`), 계획 점검 또는 미등록 점검 (FR-9) |
| 2xx이고 응답 시간 > `HTTP_SLOW_MS`(기본 3000) | 저하 |
| 2xx이고 응답 시간 ≤ 3000ms | 정상(데이터), L3 진행 |

타임아웃은 요청 시작부터 `HTTP_TIMEOUT_MS`(10000)가 **지나면**(10000ms 이상) 실패, 응답 시간 판정은 3000ms **초과**부터 저하(3000ms는 정상, 3001ms는 저하). L2가 `검증 불가`이면 L3는 하지 않는다(미점검). 응답 시간은 연결 시간을 뺀 요청→응답 완료 시간이다.

### 6.3 L3 내용
대상 설정의 `content_markers`로 정의한다. 초기값은 M1 착수 시 실제 HTML을 받아 확정한다 (§13).
- `must_contain`: 반드시 있어야 하는 문자열/정규식. 초기 안(조사 결과): `<title>온비드</title>`, `물건검색`, `공고검색`, `이용안내`, `로그인`, `/js/op_main.js`
- `maintenance_phrases`: 점검 안내 문구(예: `시스템 점검`, `서비스 점검`, `점검 중`, `일시 중단`, `이용이 불가`). 평소 화면에는 `점검`이라는 낱말이 없다(조사 §2.2)
- `block_phrases`: 차단·제한 페이지 문구(예: `Access Denied`, `Forbidden`, `Request blocked`). 평소 화면에 `차단`이라는 낱말이 한 번 나오므로 **낱말 하나로 찾지 않는다**
- `maintenance_url_patterns`: 점검 안내 페이지 경로 패턴(실제 경로는 M0에서 확인된 뒤 채움)
- `min_bytes`: 응답 크기 하한(초안 300,000바이트. 관측 약 609,185바이트)

| 조건 | 판정 |
|---|---|
| `maintenance_phrases` 감지 또는 최종 URL이 `maintenance_url_patterns`와 일치 | 원판정 `실패`(사유 `MAINTENANCE_DETECTED`), 계획 점검 또는 미등록 점검으로 분리 (FR-9) |
| `block_phrases` 감지 | 검증 불가 |
| `must_contain` 누락 또는 `min_bytes` 미만 | 실패 |
| 모두 통과 | 정상(데이터) |

추가: HTML이 참조하는 주요 JS 번들 1개를 GET해 200과 크기 하한을 확인한다 (번들 경로가 배포마다 바뀌면 HTML에서 추출).

### 6.4 L4 기능 (M3) — v0.2 변경
- 조사 결과 메인 화면을 열 때 데이터를 가져오는 XHR/fetch 요청은 **없다**. 대신 홈페이지가 의존하는 **파일 서버 요청**(`FileMngPrcsController/dnldImgFile.do?atchFileLstNo=…` 썸네일 이미지 약 15개)이 있다. HTML에서 이 주소 하나를 **매번 새로 뽑아**(번호는 바뀐다) GET만 한다. 허용 호스트 검사 적용.
- 주소 모양이 기대와 다르거나 HTML에서 찾지 못하면 `실패`가 아니라 `검증 불가`로 판정하고 등록부 갱신이 필요하다고 표시한다.

| 조건 | 판정 |
|---|---|
| 5xx / 타임아웃 | 실패 |
| 주소를 찾지 못함 / `Content-Type`이 이미지가 아님 / 모양이 다름 | 검증 불가 |
| 크기 하한 미만(0바이트 등) | 실패 |
| 이미지 1건 이상 정상 수신 | 정상(데이터) |

헤드리스 브라우저(Q4)는 서버가 HTML을 만들어 주는 구조라 **필요 없다고 확정**한다.

### 6.5 L5 신선도 (M3) — v0.2 변경
- 홈페이지 HTML에는 날짜가 없다. 이미 수집 중인 **PUBLIC 공고 목록 결과(`collected_items`)의 최신 입찰 시작일시**를 쓴다(출처가 PUBLIC인 데이터만. DEMO 데이터는 쓰지 않는다). 별도 외부 호출은 없다.
- 영업일 09:00~18:00에 최신 일시가 `FRESHNESS_MAX_HOURS`(기본 24) 넘게 지났으면 데이터 품질 `이상징후`(규칙 ID `WEB_FRESHNESS`, 출처 `WEB`)로 등록한다. 가용성 알림이 아니라 품질 이상으로 다루고, 즉시 알림은 하지 않는다. 같은 데이터로 매시 반복 탐지되어도 열린 건이 있으면 새로 만들지 않는다(기존 중복 제거).
- 영업일은 우선 **평일(월~금)** 로 정하고, 공휴일은 **결정 필요**(설정으로 목록을 둘지 후속 과제로 둘지).

### 6.6 대표 판정 우선순위
`실패` > `저하` > `검증 불가` > `미점검` > `정상(무데이터)` > `정상(데이터)`
단, `계획 점검`으로 표시된 실행은 알림·가용률 계산에서 별도 처리한다.

## 7. 데이터 모델 (제안)

**v0.2:** 아래 SQL은 v0.1의 개념 모델이며 **참고용**이다. 실제 테이블 이름·제약은 계획서 §4.2(`web_*` 접두어, 별도 `web_check_runs`)를 따른다. 대상 등록부는 DB 테이블이 아니라 파일이다(FR-1). 추가 전용 범위는 다음과 같이 조정한다:
- **추가 전용(수정·삭제 금지 트리거)**: 알림 시도 기록, 알림 멱등 키 선점 기록. 이상징후 이력은 기존 규칙 그대로.
- **서버만 쓰기, 추가 전용 아님**: 웹 점검 결과(`web_probe_results`). 기존 `probe_results`와 같은 성격이며, 보존 기간 삭제·시험 데이터 정리가 가능해야 한다.
- 보존 기간 삭제는 **전용 서버 함수 하나**만 할 수 있고(일별 요약으로 집계한 뒤 삭제), 일별 요약·재시도 큐·실행 기록의 보존 기간도 설정으로 둔다.
- 쓰기 경로: 상태 전환·이상징후·알림 기록은 **한 DB 트랜잭션의 함수**로 저장한다(업무 변경과 이력을 함께 저장한다는 기존 원칙). 계획 점검 창의 등록·취소는 팀장 확인을 하는 DB 함수로만 한다(테이블 직접 쓰기 정책 없음).

```sql
-- (v0.1 개념 모델, 참고용) 등록부는 파일로 대체되었음
alter table targets add column kind text not null default 'api' check (kind in ('api','web'));
alter table targets add column web_config jsonb;  -- url, timeout_ms, content_markers, functional_requests ...

-- 웹 점검 결과 (프로브 단위)
create table web_probe_results (
  id bigint generated always as identity primary key,
  run_id bigint not null references check_runs(id),
  target_id bigint not null references targets(id),
  layer text not null check (layer in ('L1','L2','L3','L4','L5')),
  verdict text not null,              -- 기존 판정 enum 재사용
  is_confirm_retry boolean not null default false,
  http_status int,
  duration_ms int,
  final_url text,
  cert_days_left int,
  detail jsonb,                       -- 누락 표식, 오류 메시지 등 (응답 본문 전체 저장 금지)
  observed_at timestamptz not null default now()
);

-- 대상별 현재 상태 (상태 전환 판단용)
create table target_state (
  target_id bigint primary key references targets(id),
  current_verdict text not null,
  since timestamptz not null,
  consecutive_degraded int not null default 0,
  consecutive_unverifiable int not null default 0,
  open_incident_id bigint,
  last_alert_at timestamptz
);

-- 계획 점검 창
create table maintenance_windows (
  id bigint generated always as identity primary key,
  target_id bigint references targets(id),  -- null이면 전체
  starts_at timestamptz not null,
  ends_at timestamptz not null check (ends_at > starts_at),
  reason text,
  created_by uuid not null,
  created_at timestamptz not null default now()
);

-- 알림 발송 기록 (추가 전용)
create table notifications (
  id bigint generated always as identity primary key,
  idempotency_key text not null unique,
  channel text not null,               -- 'telegram'
  event_type text not null,            -- down, degraded, recovered, ongoing, cert, unverifiable, stale, unplanned_maintenance
  target_id bigint references targets(id),
  incident_id bigint,
  status text not null,                -- sent, failed
  attempts int not null default 1,
  response_code int,
  created_at timestamptz not null default now()
);
```

- 모든 신규 테이블에 RLS를 적용한다 (기존 규칙: 로그인한 팀 계정만 조회, 쓰기 정책은 두지 않고 쓰기는 서버 역할·DB 함수만).
- `notifications`(알림 시도 기록)는 추가 전용이다 (수정·삭제 금지 트리거, 기존 이력 테이블과 동일). **판정 결과는 추가 전용이 아니다**(위 참고).
- 응답 본문 전체는 저장하지 않는다. 판정 근거가 되는 최소 정보만 `detail`에 둔다.
- 보존 기간: `web_probe_results` 90일 (설정 가능). 보존 기간이 지나면 일별 요약으로 집계한 뒤 삭제하는 작업을 둔다.

## 8. 알림 메시지 형식

텔레그램 `sendMessage`, `parse_mode=HTML`. 한국시간(KST)으로 표기한다.

```
🔴 [온비드 홈페이지] 장애 감지
시각: 2026-11-04 14:07 KST (재확인 14:09)
판정: 실패 — L2 HTTP 503
응답시간: 10,000ms(타임아웃)
상세: https://onbid-ops-radar.vercel.app/anomalies/123
```

```
🟢 [온비드 홈페이지] 복구
시각: 2026-11-04 16:07 KST
장애 지속: 약 2시간 (14:07 ~ 16:07, 1시간 간격 관측 기준)
상세: https://onbid-ops-radar.vercel.app/anomalies/123
```

- 지속 시간에는 관측 간격의 오차가 있다고 표기한다.
- 메시지에 비밀값, 내부 요청 헤더, 개인정보를 넣지 않는다.
- **OpenAPI 점검 결과 문구는 넣지 않는다**(v0.1의 "OpenAPI 최근 점검: 정상"은 "서비스 전체가 정상이라고 주장하지 않는다"는 도메인 규칙과 부딪힐 수 있어 뺐다).
- `parse_mode=HTML`이므로 메시지에 들어가는 모든 동적 값(오류 문구 등)은 HTML 특수문자를 이스케이프한다.
- 앱 주소는 서버 환경변수(`APP_BASE_URL`, 앱 쪽 알림용)와 Vault의 앱 주소(DB 쪽 감시용)에서 가져온다. 같은 값이며 한쪽만 바뀌지 않게 운영 문서에 적는다.
- 모니터 정지 알림 문구(⚫)는 SQL 함수에서 만들어 한 곳에서만 관리한다.

## 9. 설정값 (기존 설정 모듈에 추가)

| 키 | 기본값 | 설명 |
|---|---|---|
| `WEB_CHECK_CRON` | `7 * * * *` | 매시간 점검 스케줄. `pg_cron`은 UTC로 해석하며 한국이 UTC+9(정시 차이)라 **UTC·KST 모두 같은 값**이다(Q8 해결). 설정 테이블이 아니라 스케줄러 등록 스크립트가 관리 |
| `HTTP_TIMEOUT_MS` | 10000 | L2 타임아웃 |
| `HTTP_SLOW_MS` | 3000 | 저하 기준 |
| `CONFIRM_RETRY_DELAY_SEC` | 90 | 확인 재시도 간격 |
| `REALERT_AFTER_HOURS` | 3 | 장애 지속 재알림 간격 |
| `DEGRADED_ALERT_COUNT` | 2 | 저하 알림 연속 횟수 |
| `UNVERIFIABLE_ALERT_COUNT` | 3 | 검증 불가 알림 연속 횟수 |
| `CERT_WARN_DAYS` | 14 | 인증서 경고 |
| `HEARTBEAT_STALE_MIN` | 130 | 모니터 정지 판단 |
| `FRESHNESS_MAX_HOURS` | 24 | L5 신선도 |
| `WEB_RESULT_RETENTION_DAYS` | 90 | 결과 보존 기간 |
| `AUX_ALERT_COUNT` | 3 | 보조 확인 이상 알림 연속 횟수 (v0.2) |
| `HEARTBEAT_REALERT_HOURS` | 24 | 모니터 정지 재알림 간격 (v0.2) |
| `WEB_ALERT_DAILY_CAP` | 12 | 대상별 하루 알림 상한 (v0.2, FR-12) |
| `WEB_RUN_TIME_LIMIT_SEC` | 60 | 웹 점검 실행 시간 예산 (v0.2, 기존 API 점검 설정과 별개) |
| `WEB_MONITOR_ENABLED` | true | 웹 점검 전체 켜기/끄기 (v0.2, FR-12) |
| `WEB_NOTIFY_TIMEOUT_MS` | 5000 | 텔레그램 요청 타임아웃 (v0.2) |

| `TELEGRAM_CHAT_ID` | (secret) | 서버 전용. 위와 같은 두 곳 |

설정 키는 계획서 §4.4의 대응표(`web_` 접두어, 범위·관계 검사 포함)를 따른다. 범위 조정: 요청 타임아웃 최대 30000ms, `HEARTBEAT_STALE_MIN` 최소 90분(1시간 주기 + 여유). **웹 설정은 기존 `settings` 테이블에 넣지 않고 별도 테이블 `web_settings`에 둔다**(기존 설정 읽기는 모르는 키를 오류로 거부해, 같은 테이블에 넣으면 OpenAPI 점검·대시보드·보고서가 멈춘다). 그래서 웹 설정이 틀려도 웹 점검만 멈추고 기존 점검에는 영향이 없다. (v0.1의 "기존 설정 모듈에 추가"는 "기존 설정 모듈의 방식을 따르되 테이블은 분리"로 바뀌었다.) 개발·시험에서 실제 알림이 나가지 않도록 알림 방식은 환경변수 `WEB_NOTIFY_MODE`(`telegram`/`log`)로 고르고 운영 배포에서만 `telegram`이다.

## 10. 비기능 요구사항

- **부하**: `web` 대상 1개당 1시간에 L1~L3(`main.do` 1, 진입 스텁 1, 대기열 설정 1, JS 번들 1~2) + L4 이미지 1 = **약 5~7개 요청**, 확인 재시도가 있으면 한 번 더. 동시 요청 금지, 요청 사이 간격 유지(약 0.5초). (v0.1의 "2~3개 + 3개 이하"를 실제 구조에 맞게 바로잡음. C2 승인 때 말씀드린 "2~3회"보다 늘어난 값이다.)
- **User-Agent**: 모니터임을 알 수 있는 고정 값 사용 (예: `OnBidOpsRadar-Monitor/1.0`). 개인 이메일 등 개인정보 넣지 않음.
- **관측 지점**: 점검 함수 리전을 서울(`icn1`)로 고정한다. 설치된 Next.js 16에서 `preferredRegion`은 사용 중지라서 **프로젝트 설정 파일 `vercel.json`의 `regions`** 로 정한다(수동 점검 서버 액션도 같은 리전에서 실행된다). 해외 IP 차단·WAF로 인한 오탐을 피하기 위함이다.
- **실행 시간**: 매시간 실행은 웹 전용 시간 예산(`WEB_RUN_TIME_LIMIT_SEC`, 기본 60초) 안에서 끝낸다. 요청 타임아웃은 남은 예산을 넘기지 않으며, 순차 실행의 정상 소요는 수 초(조사 기준 1~2초대 요청)다. 확인 재시도는 별도 실행으로 예약한다 (한 실행 안에서 90초 대기 금지). 점검 경로 `maxDuration`은 90초다.
- **신뢰성**: 한 대상·한 프로브의 오류가 다른 대상 점검을 멈추지 않는다 (기존 원칙).
- **보안**: 기존 원칙 유지 (서버·DB 단 권한 검사, RLS, 비밀키 비노출). 텔레그램 토큰이 유출되면 즉시 교체할 수 있도록 절차를 docs에 적는다(토큰이 **두 곳**(Vercel·Vault)에 있으므로 두 곳을 함께 바꾼다). 크론 등록 스크립트의 미리 보기 출력에 **모든 비밀값이 가려지게** 한다.
- **문서화 위치**: 웹 대상·L4 요청 정보는 `docs/web-monitor-*.md`에 쓴다(`docs/api-registry.md`는 명세서에서 생성하는 파일이라 손으로 고치지 않는다).
- **기관 보안 지침**: 업무 알림을 텔레그램으로 받는 것이 내부 지침상 허용되는지 확인한다. 허용되지 않으면 `Notifier` 구현체만 교체한다 (이메일, 사내 메신저 웹훅).

## 11. 수용 기준

### M1 (L1~L3 + 스케줄)
- [ ] `data/registry/web-targets.json`에 `onbid-home`(진입 스텁 + `main.do`)이 있고, 기존 API 점검 결과·기존 점검 기록·누락 감지가 바뀌지 않는다 (회귀 시험 통과).
- [ ] 매시간 스케줄이 운영 환경에서 연속 24회 실행된 기록이 있다.
- [ ] 단위 시험: §6.1~6.3 표의 모든 행과 경계값(타임아웃 10000ms 이상, 응답 3000ms/3001ms, 인증서 14일/15일, 401·403·404·410·429와 그 밖의 4xx, 리다이렉트 10/11회, 허용 호스트 밖 이동)에 시험이 있다.
- [ ] 목(mock) 서버로 503, 타임아웃, 점검 문구, 표식 누락, 차단 페이지, 이동 스텁에서 이동 코드가 사라진 경우를 재현해 기대 판정이 나온다.
- [ ] Vercel 서울 리전에서 실제로 홈페이지 점검이 성공한다(W00-1 확인, 결과를 문서에 기록).
- [ ] 신규 테이블 RLS 시험과 추가 전용 시험이 통과한다.

### M2 (알림 + 이상징후 + 자체 감시)
- [ ] 목 서버로 정상→실패→정상 시나리오를 돌리면 알림이 정확히 2건(장애, 복구) 발송된다.
- [ ] 1회 실패 후 재시도 정상이면 알림 0건, 일시 실패 1건이 기록된다.
- [ ] 장애가 지속되면 마지막 알림 후 3시간 이상 지난 점검마다 지속 알림이 나간다(경계 시험: 2시간 59분 미발송 / 3시간 00분 발송). 매시 실패가 7시간 이어지면 지속 알림이 2건 추가된다.
- [ ] 같은 사건에 대해 실행이 중복돼도 같은 알림이 중복 발송되지 않고, 장애 지속처럼 같은 사건의 **반복 알림은 막히지 않는다** (사건 종류별 멱등 키 시험).
- [ ] 텔레그램 API 실패(5xx)를 목으로 재현하면 3회 재시도 후 실패로 기록되고 대시보드에 표시된다.
- [ ] 매시간 작업을 멈추면 정상 종료 실행이 130분 지난 뒤 감시 작업의 다음 실행(10분 주기)에서 모니터 정지 알림이 온다. 이후 24시간마다 재알림, 재개 시 재개 알림.
- [ ] 확정 실패 시 이상징후가 1건 생성되고, 지속 중에는 새 건이 생기지 않는다.
- [ ] 계획 점검 창 안의 실패는 알림·가용률·이상징후에서 제외된다. 창 밖에서 점검 문구가 감지되면 장애 알림 없이 `미등록 점검 감지` 1건이 나간다.
- [ ] 수동 점검은 현재 상태·사건·알림을 바꾸지 않는다.
- [ ] `web_monitor_enabled`를 끄면 점검·재시도·알림이 멈추고 기존 API 점검은 영향이 없다. 하루 알림 상한을 넘으면 억제 알림 1건이 나간다.
- [ ] 인증서 만료 14일 이내에도 대표 판정이 저하로 묶이지 않고 인증서 알림만 하루 1회 나간다.
- [ ] 실제 텔레그램으로 시험 메시지 1건 수신을 확인한다 (수동 확인, 결과를 docs에 기록).

### M3 (L4·L5 + 대시보드/보고서)
- [ ] L4(썸네일 이미지 요청) 대상과 판정 규칙이 `docs/web-monitor-*.md`에 문서화되어 있고, 주소 모양이 바뀌면 검증 불가로 판정된다. L5는 PUBLIC 수집 결과만 사용한다.
- [ ] 대시보드 홈페이지 카드, `/web` 화면(24시간 스트립·실행 이력·알림 기록·계획 점검 창)이 모바일에서도 보이고 팀장만 창 등록·수동 점검을 할 수 있다 (화면 시험).
- [ ] 일일 점검보고서에 홈페이지 절이 들어가고 가용률 계산식이 §FR-10과 일치한다.

## 14. 위험

- **오탐으로 인한 알림 피로**: 확인 재시도, 상태 전환 알림, 4xx를 검증 불가로 분리하는 것으로 줄인다. 1주 관찰 기간을 반드시 둔다.
- **비공개 요청(L4)의 변경**: 실패가 아니라 검증 불가로 처리하고 등록부 갱신 알림으로 다룬다.
- **해외 IP/WAF 차단**: 서울 리전 고정, 차단 문구는 검증 불가로 처리한다. 첫 주에 사무실 브라우저 결과와 대조한다.
- **관측 한계의 과대 해석**: 단일 지점·1시간 간격 외부 관측이라는 점을 화면·보고서·알림에 명시한다. 간격 사이의 짧은 장애는 탐지하지 못한다.
- **토큰 만료**: 기존 Vercel·Supabase·GitHub 토큰 만료(약 30일) 관리 일정에 텔레그램 토큰 점검을 함께 넣는다.
