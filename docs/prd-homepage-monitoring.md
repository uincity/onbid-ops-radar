# PRD: 온비드 홈페이지 가용성 모니터링 및 알림 (OnBid Ops Radar 확장)

- 문서 버전: v0.1 (초안)
- 작성일: 2026-11-04
- 상위 문서: PRD v2.1 (OnBid Ops Radar), docs/api-registry.md
- 상태: 초안. 구현 착수 전 §13의 미결정 사항을 확정할 것

---

## 0. Claude Code 작업 지침 (먼저 읽을 것)

이 문서는 기존 OnBid Ops Radar 저장소에 기능을 **추가**하기 위한 PRD다. 새 서비스를 만들지 않는다.

1. 구현 전에 기존 코드에서 아래를 먼저 찾아 읽고, 그 패턴을 그대로 따른다.
   - 서비스 등록부 (docs/api-registry.md 및 등록부를 담은 코드/테이블)
   - 6가지 판정 로직 (정상(데이터) / 정상(무데이터) / 저하 / 실패 / 검증 불가 / 미점검)
   - 이상징후 생성 및 중복 제거 로직
   - Supabase 스케줄러(pg_cron 등) 설정과 08:30 실행 여부 확인 로직
   - 설정값을 한곳에서 관리하는 모듈
2. 기존 판정 체계와 테이블을 **확장**한다. 같은 목적의 새 체계를 따로 만들지 않는다.
3. 기능마다 단위·DB·화면 시험을 함께 작성한다 (기존 방식: 단위 / DB(RLS 포함) / 화면).
4. 온비드에 보내는 요청은 **읽기 전용 GET만** 허용한다. 로그인, 폼 제출, 쓰기 요청은 금지.
5. 비밀값(텔레그램 봇 토큰 등)은 서버 환경변수/Supabase secrets에만 둔다. 브라우저 번들, 로그, DB 평문, 커밋에 넣지 않는다.
6. 마일스톤(§12) 순서대로 진행하고, 각 단계가 끝나면 수용 기준(§11)으로 검증한 뒤 다음 단계로 넘어간다.
7. 이 문서와 기존 코드가 충돌하면 임의로 정하지 말고 충돌 내용을 보고한다.

## 1. 배경

- 현재 OnBid Ops Radar는 온비드 OpenAPI 26종(오퍼레이션 29개)을 **매일 08:00에 1회** 점검한다.
- 온비드 **홈페이지(https://www.onbid.co.kr/)** 자체의 가용성은 점검하지 않는다. 일과 중에 장애가 나면 다음 날 점검 때까지, 또는 이용자 문의가 올 때까지 알 수 없다.
- 결과는 대시보드에서만 볼 수 있다. 담당자가 화면을 열지 않으면 이상을 알 수 없다 (푸시 알림 없음).
- 사전 관찰: 메인 페이지를 단순 HTTP로 받으면 본문이 거의 없고 `<title>온비드</title>` 정도만 오는 것으로 보인다. 화면을 클라이언트 측 JS로 그리는 구조로 추정된다. 따라서 **HTTP 200만으로는 정상 판정을 할 수 없다.**

## 2. 목표 / 비목표

### 목표
- G1. 온비드 홈페이지를 **1시간 간격**(설정 가능)으로 외부 이용자 관점에서 점검한다.
- G2. 접속 → HTTP → 내용 → 기능 → 신선도의 층별 점검으로 "껍데기만 뜨는 장애"까지 잡는다.
- G3. 상태가 바뀌면(정상→실패, 실패→정상) **텔레그램으로 알림**을 보낸다. 채널은 교체할 수 있게 만든다.
- G4. 알림과 동시에 기존 이상징후로 등록해 배정·조치·이력 흐름을 그대로 쓴다.
- G5. 모니터 자체가 멈추면 이를 감지해 알린다 (dead-man switch).

### 비목표
- 온비드 내부 서버 지표(CPU, DB, 전체 이용자 성공률) 수집. 외부 관측만 한다.
- 로그인이 필요한 화면, 입찰 등 쓰기 동작의 점검.
- 다지점(여러 지역/통신사) 관측. 1차 범위는 단일 관측 지점.
- 기존 API 일일 점검의 주기 변경 (08:00 1회 유지).

## 3. 용어

| 용어 | 정의 |
|---|---|
| 점검 대상(target) | 등록부의 한 항목. 기존 API 서비스 외에 `kind = 'web'`인 대상이 추가됨 |
| 프로브(probe) | 한 대상에 대한 한 층의 점검 단위 (예: tls, http, content) |
| 점검 실행(run) | 스케줄 1회분. 여러 대상·프로브를 포함 |
| 확인 재시도(confirm retry) | 실패 시 짧은 간격을 두고 한 번 더 확인하는 것 |
| 상태 전환 | 대상의 대표 판정이 정상 계열 ↔ 실패 계열로 바뀌는 것 |
| 계획 점검 창(maintenance window) | 온비드가 예고한 점검 시간. 이 시간의 실패는 알림·가용률에서 제외 |

## 4. 사용자

- 팀장 1명, 운영 담당자 1명 (기존 계정과 동일).
- 알림 수신: 위 2명의 텔레그램 (개인 chat 또는 그룹 chat 1개).

## 5. 기능 요구사항

### FR-1. 점검 대상 등록
- 등록부에 `kind` 필드를 추가한다 (`api` | `web`). 기존 항목은 `api`로 이전한다.
- 초기 `web` 대상: `onbid-home` = `https://www.onbid.co.kr/`.
- 대상별 설정: 점검 주기, 타임아웃, 활성 여부, 프로브 목록, 내용 표식(§6.3), 알림 여부.

### FR-2. 층별 프로브 (§6 상세)
- L1 접속: DNS 조회, TCP/TLS 연결, 인증서 만료까지 남은 일수.
- L2 HTTP: 상태 코드, 총 응답 시간, 리다이렉트 체인, 최종 URL.
- L3 내용: 필수 표식 존재, 점검 안내 문구 부재, 응답 크기 하한.
- L4 기능: 메인 화면이 쓰는 데이터 요청(XHR/fetch) 1~3개를 직접 호출해 목록이 채워지는지 확인.
- L5 신선도: 최신 공고/공지의 날짜가 기준 시간 안에 있는지 확인 (영업일 기준).
- 1차 구현(M1)은 L1~L3, L4·L5는 M3.

### FR-3. 판정
- 프로브별로 기존 6가지 판정 중 하나를 낸다.
- 대상의 대표 판정 = 가장 나쁜 프로브 판정 (우선순위 §6.6).
- 판정 규칙은 결정적이어야 한다 (같은 입력 → 같은 판정).

### FR-4. 확인 재시도
- 대표 판정이 `실패`이면 `CONFIRM_RETRY_DELAY_SEC`(기본 90초) 뒤 같은 대상을 1회 재점검한다.
- 재점검도 `실패`일 때만 확정 실패로 기록하고 알림 대상으로 삼는다.
- 재점검이 정상이면 `일시 실패(flap)`로 기록만 하고 알림하지 않는다 (이상징후 미등록, 통계에는 남김).

### FR-5. 스케줄
- 기존 Supabase 스케줄러에 매시간 작업을 추가한다. 기본은 매시 정각이 아닌 `:07`분 (설정 가능).
- 매시간 작업은 `web` 대상만 돈다. `api` 일일 점검과 서로 독립적이다.
- 실행 시간 상한을 지킨다. 대상이 늘어나도 한 실행이 플랫폼 제한(현재 80초)을 넘지 않게 대상별 타임아웃 합계를 검증한다.

### FR-6. 알림
- 알림은 **상태 전환 시에만** 보낸다.
  - 정상 계열 → 확정 실패: `🔴 장애 감지`
  - 정상 → 저하가 2회 연속: `🟠 성능 저하`
  - 실패/저하 → 정상: `🟢 복구` (지속 시간 포함)
- 실패가 이어지면 `REALERT_AFTER_HOURS`(기본 3시간)마다 `⏳ 장애 지속` 알림 1회.
- 인증서 만료 `CERT_WARN_DAYS`(기본 14일) 이내: 하루 1회 `🟡 인증서 만료 임박`.
- `검증 불가` / `미점검`은 즉시 알림하지 않는다. 같은 대상에서 연속 `UNVERIFIABLE_ALERT_COUNT`(기본 3회)가 되면 `⚪ 점검 불가 지속` 알림.
- 알림 채널은 인터페이스(`Notifier`)로 분리하고 1차 구현체는 `TelegramNotifier`.
- 알림 발송 결과(성공/실패, 응답 코드)는 기록한다. 발송 실패는 최대 3회 재시도하고, 그래도 실패하면 대시보드에 표시한다.
- 같은 사건에 대한 중복 발송을 막기 위해 `(target_id, event_type, incident_id)`로 멱등 키를 둔다.

### FR-7. 이상징후 연동
- 확정 실패/저하 지속 시 기존 이상징후를 생성한다 (유형: `web_availability`).
- 같은 대상의 열린 이상징후가 있으면 새로 만들지 않고 발생 기록만 추가한다 (기존 중복 제거 규칙).
- 복구되면 자동으로 종결하지 않는다. 이상징후에 `복구 확인됨` 표시만 하고, 종결은 담당자가 한다 (기존 처리 흐름 유지).
- 알림 메시지에 이상징후 상세 화면 링크를 넣는다.

### FR-8. 모니터 자체 감시 (dead-man switch)
- `HEARTBEAT_STALE_MIN`(기본 130분) 동안 `web` 점검 실행 기록이 없으면 `⚫ 모니터 정지` 알림을 보낸다.
- 감시 주체는 매시간 점검과 다른 실행 경로여야 한다 (예: 별도 pg_cron 작업이 DB만 조회). 점검 함수가 죽어도 감시가 돌아야 한다.
- 기존 08:30 일일 점검 실행 확인과 같은 방식으로 구현한다.

### FR-9. 계획 점검 창
- 관리자가 대시보드에서 점검 창(시작~종료, 사유)을 등록할 수 있다.
- 창 안의 실패는 판정은 기록하되 알림·가용률 계산·이상징후 생성에서 제외하고 `계획 점검`으로 표시한다.
- L3에서 점검 안내 문구가 감지됐는데 등록된 창이 없으면 `🔧 미등록 점검 감지` 알림 1회 (실패 알림 대신).

### FR-10. 대시보드/보고서
- 대시보드에 "홈페이지" 카드: 현재 상태, 최근 24시간 시간대별 판정 스트립, 최근 응답 시간, 인증서 남은 일수.
- 일일 점검보고서에 홈페이지 절을 추가한다: 24회 중 판정 분포, 확정 장애 건수와 총 지속 시간, 일시 실패 횟수, 평균/최대 응답 시간.
- 가용률은 `정상 계열 / (판정 횟수 − 검증 불가 − 미점검 − 계획 점검)`. 화면에 "단일 지점, 1시간 간격 외부 관측"이라고 명시한다.

### FR-11. 수동 점검
- 대시보드에서 `web` 대상 즉시 점검 버튼 (기존 수동 점검 기능 확장). 수동 점검 결과로는 알림을 보내지 않는다 (설정으로 변경 가능).

## 6. 판정 규칙 상세

모든 임계값은 설정 모듈에서 관리한다. 아래 값은 기본값이며 첫 1주 관찰 뒤 조정한다.

### 6.1 L1 접속
| 조건 | 판정 |
|---|---|
| DNS 실패, TCP 연결 실패, TLS 핸드셰이크 실패 | 실패 |
| 인증서 만료됨 / 호스트명 불일치 | 실패 |
| 인증서 만료 14일 이내 | 저하 (+ 인증서 알림) |
| 그 외 | 정상(데이터) |

### 6.2 L2 HTTP
| 조건 | 판정 |
|---|---|
| 타임아웃 (`HTTP_TIMEOUT_MS` 기본 10000) | 실패 |
| 5xx | 실패 |
| 4xx (403, 429 포함) | 검증 불가. 차단/제한 가능성이 있으므로 실패로 세지 않음. 연속이면 FR-6 규칙으로 알림 |
| 리다이렉트 10회 초과 | 실패 |
| 최종 URL이 점검 안내 경로 패턴과 일치 | 계획 점검 또는 미등록 점검 (FR-9) |
| 2xx이고 응답 시간 > `HTTP_SLOW_MS`(기본 3000) | 저하 |
| 2xx이고 응답 시간 ≤ 3000ms | 정상(데이터), L3 진행 |

### 6.3 L3 내용
대상 설정의 `content_markers`로 정의한다. 초기값은 M1 착수 시 실제 HTML을 받아 확정한다 (§13).
- `must_contain`: 반드시 있어야 하는 문자열/정규식 (예: `<title>온비드</title>`, 주요 JS 번들 경로 패턴)
- `must_not_contain`: 있으면 안 되는 문자열 (예: `시스템 점검`, `서비스 일시 중단`, `점검 중`, WAF 차단 페이지 특유 문구)
- `min_bytes`: 응답 크기 하한

| 조건 | 판정 |
|---|---|
| `must_not_contain` 중 점검 문구 감지 | 계획 점검 또는 미등록 점검 (FR-9) |
| `must_not_contain` 중 차단 문구 감지 | 검증 불가 |
| `must_contain` 누락 또는 `min_bytes` 미만 | 실패 |
| 모두 통과 | 정상(데이터) |

추가: HTML이 참조하는 주요 JS 번들 1개를 GET해 200과 크기 하한을 확인한다 (번들 경로가 배포마다 바뀌면 HTML에서 추출).

### 6.4 L4 기능 (M3)
- 메인 화면이 부르는 데이터 요청을 브라우저 개발자도구로 찾아 `functional_requests`로 등록한다 (URL, 메서드는 GET만, 필수 헤더, 기대 응답 형태).
- 이 요청들은 **공개 규격이 아니다.** 응답 구조가 기대와 다르면 `실패`가 아니라 `검증 불가`로 판정하고, 등록부 갱신이 필요하다고 표시한다.

| 조건 | 판정 |
|---|---|
| 5xx / 타임아웃 | 실패 |
| 응답 구조 불일치 / 파싱 불가 | 검증 불가 |
| 목록 0건 | 정상(무데이터). 영업일 일과 시간에 연속 2회면 저하 |
| 목록 1건 이상 | 정상(데이터) |

선택: 헤드리스 브라우저(Playwright) 점검은 Vercel 함수 제한 때문에 매시간 경로에 넣지 않는다. 필요하면 별도 실행 환경(GitHub Actions 스케줄 등)에서 하루 2~3회 돌리고 결과를 같은 테이블에 적재한다 (§13 결정 필요).

### 6.5 L5 신선도 (M3)
- L4 응답에서 최신 공고/공지 일시를 추출한다.
- 영업일 09:00~18:00에 최신 일시가 `FRESHNESS_MAX_HOURS`(기본 24) 넘게 지났으면 `이상징후`(데이터 품질)로 등록한다. 가용성 알림이 아니라 품질 이상으로 다루고, 즉시 알림은 하지 않는다.

### 6.6 대표 판정 우선순위
`실패` > `저하` > `검증 불가` > `미점검` > `정상(무데이터)` > `정상(데이터)`
단, `계획 점검`으로 표시된 실행은 알림·가용률 계산에서 별도 처리한다.

## 7. 데이터 모델 (제안)

기존 스키마 명명 규칙을 우선한다. 아래는 개념 모델이며 기존 테이블로 흡수할 수 있으면 흡수한다.

```sql
-- 등록부 확장
alter table targets add column kind text not null default 'api' check (kind in ('api','web'));
alter table targets add column web_config jsonb;  -- url, timeout_ms, content_markers, functional_requests ...

-- 웹 점검 결과 (프로브 단위)
create table web_probe_results (
  id bigint generated always as identity primary key,
  run_id bigint not null references check_runs(id),
  target_id bigint not null references targets(id),
  layer text not null check (layer in ('L1','L2','L3','L4','L5')),
  verdict text not null,              -- 기존 판정 enum 재사용
  is_confirm_retry boolean not null default false,
  http_status int,
  duration_ms int,
  final_url text,
  cert_days_left int,
  detail jsonb,                       -- 누락 표식, 오류 메시지 등 (응답 본문 전체 저장 금지)
  observed_at timestamptz not null default now()
);

-- 대상별 현재 상태 (상태 전환 판단용)
create table target_state (
  target_id bigint primary key references targets(id),
  current_verdict text not null,
  since timestamptz not null,
  consecutive_degraded int not null default 0,
  consecutive_unverifiable int not null default 0,
  open_incident_id bigint,
  last_alert_at timestamptz
);

-- 계획 점검 창
create table maintenance_windows (
  id bigint generated always as identity primary key,
  target_id bigint references targets(id),  -- null이면 전체
  starts_at timestamptz not null,
  ends_at timestamptz not null check (ends_at > starts_at),
  reason text,
  created_by uuid not null,
  created_at timestamptz not null default now()
);

-- 알림 발송 기록 (추가 전용)
create table notifications (
  id bigint generated always as identity primary key,
  idempotency_key text not null unique,
  channel text not null,               -- 'telegram'
  event_type text not null,            -- down, degraded, recovered, ongoing, cert, unverifiable, stale, unplanned_maintenance
  target_id bigint references targets(id),
  incident_id bigint,
  status text not null,                -- sent, failed
  attempts int not null default 1,
  response_code int,
  created_at timestamptz not null default now()
);
```

- 모든 신규 테이블에 RLS를 적용한다 (기존 규칙: 로그인한 팀 계정만 조회, 쓰기는 서버 역할만).
- `notifications`, 판정 결과는 추가 전용이다 (수정·삭제 금지 트리거, 기존 이력 테이블과 동일).
- 응답 본문 전체는 저장하지 않는다. 판정 근거가 되는 최소 정보만 `detail`에 둔다.
- 보존 기간: `web_probe_results` 90일 (설정 가능). 보존 기간이 지나면 일별 요약으로 집계한 뒤 삭제하는 작업을 둔다.

## 8. 알림 메시지 형식

텔레그램 `sendMessage`, `parse_mode=HTML`. 한국시간(KST)으로 표기한다.

```
🔴 [온비드 홈페이지] 장애 감지
시각: 2026-11-04 14:07 KST (재확인 14:09)
판정: 실패 — L2 HTTP 503
응답시간: 10,000ms(타임아웃)
OpenAPI 최근 점검: 정상 (08:00)
상세: https://onbid-ops-radar.vercel.app/incidents/123
```

```
🟢 [온비드 홈페이지] 복구
시각: 2026-11-04 16:07 KST
장애 지속: 약 2시간 (14:07 ~ 16:07, 1시간 간격 관측 기준)
상세: https://onbid-ops-radar.vercel.app/incidents/123
```

- 지속 시간에는 관측 간격의 오차가 있다고 표기한다.
- 메시지에 비밀값, 내부 요청 헤더, 개인정보를 넣지 않는다.

## 10. 비기능 요구사항

- **부하**: `web` 대상당 1시간에 최대 (L1~L3 요청 2~3개 + L4 요청 3개 이하) × 재시도 1회. 동시 요청 금지, 요청 사이 간격 유지.
- **User-Agent**: 모니터임을 알 수 있는 고정 값 사용 (예: `OnBidOpsRadar-Monitor/1.0`). 개인 이메일 등 개인정보 넣지 않음.
- **관측 지점**: 점검 함수 리전을 서울(`icn1`)로 고정한다. 해외 IP 차단·WAF로 인한 오탐을 피하기 위함.
- **실행 시간**: 매시간 실행은 60초 안에 끝나는 것을 목표로 하고, 확인 재시도는 별도 실행으로 예약한다 (한 실행 안에서 90초 대기 금지).
- **신뢰성**: 한 대상·한 프로브의 오류가 다른 대상 점검을 멈추지 않는다 (기존 원칙).
- **보안**: 기존 원칙 유지 (서버·DB 단 권한 검사, RLS, 비밀키 비노출). 텔레그램 토큰이 유출되면 즉시 교체할 수 있도록 절차를 docs에 적는다.
- **기관 보안 지침**: 업무 알림을 텔레그램으로 받는 것이 내부 지침상 허용되는지 확인한다. 허용되지 않으면 `Notifier` 구현체만 교체한다 (이메일, 사내 메신저 웹훅).

## 11. 수용 기준

### M1 (L1~L3 + 스케줄)
- [ ] 등록부에 `onbid-home`이 `kind='web'`으로 있고, 기존 `api` 대상 점검 결과가 바뀌지 않는다 (회귀 시험 통과).
- [ ] 매시간 스케줄이 운영 환경에서 연속 24회 실행된 기록이 있다.
- [ ] 단위 시험: §6.1~6.3 표의 모든 행과 경계값(타임아웃 정확히 10000ms, 3000ms, 인증서 14일/15일, 4xx 각 코드)에 시험이 있다.
- [ ] 목(mock) 서버로 503, 타임아웃, 점검 문구, 표식 누락, 차단 페이지를 재현해 기대 판정이 나온다.
- [ ] 신규 테이블 RLS 시험과 추가 전용 시험이 통과한다.

### M2 (알림 + 이상징후 + 자체 감시)
- [ ] 목 서버로 정상→실패→정상 시나리오를 돌리면 알림이 정확히 2건(장애, 복구) 발송된다.
- [ ] 1회 실패 후 재시도 정상이면 알림 0건, 일시 실패 1건이 기록된다.
- [ ] 장애가 7시간 지속되면 장애 지속 알림이 2건(3h, 6h) 추가된다.
- [ ] 같은 사건에 대해 실행이 중복돼도 알림이 중복 발송되지 않는다 (멱등 키 시험).
- [ ] 텔레그램 API 실패(5xx)를 목으로 재현하면 3회 재시도 후 실패로 기록되고 대시보드에 표시된다.
- [ ] 매시간 작업을 멈추면 130분 안에 모니터 정지 알림이 온다.
- [ ] 확정 실패 시 이상징후가 1건 생성되고, 지속 중에는 새 건이 생기지 않는다.
- [ ] 계획 점검 창 안의 실패는 알림·가용률·이상징후에서 제외된다.
- [ ] 실제 텔레그램으로 시험 메시지 1건 수신을 확인한다 (수동 확인, 결과를 docs에 기록).

### M3 (L4·L5 + 대시보드/보고서)
- [ ] L4 요청 목록이 등록부에 문서화되어 있고 (docs/api-registry.md 또는 별도 문서), 응답 구조가 바뀌면 검증 불가로 판정된다.
- [ ] 대시보드 홈페이지 카드와 24시간 스트립이 모바일에서도 보인다 (화면 시험).
- [ ] 일일 점검보고서에 홈페이지 절이 들어가고 가용률 계산식이 §FR-10과 일치한다.

## 14. 위험

- **오탐으로 인한 알림 피로**: 확인 재시도, 상태 전환 알림, 4xx를 검증 불가로 분리하는 것으로 줄인다. 1주 관찰 기간을 반드시 둔다.
- **비공개 요청(L4)의 변경**: 실패가 아니라 검증 불가로 처리하고 등록부 갱신 알림으로 다룬다.
- **해외 IP/WAF 차단**: 서울 리전 고정, 차단 문구는 검증 불가로 처리한다. 첫 주에 사무실 브라우저 결과와 대조한다.
- **관측 한계의 과대 해석**: 단일 지점·1시간 간격 외부 관측이라는 점을 화면·보고서·알림에 명시한다. 간격 사이의 짧은 장애는 탐지하지 못한다.
- **토큰 만료**: 기존 Vercel·Supabase·GitHub 토큰 만료(약 30일) 관리 일정에 텔레그램 토큰 점검을 함께 넣는다.
