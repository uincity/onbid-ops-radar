## 1. 무엇을 만드는가 (한 문단)

지금은 온비드 **OpenAPI**만 하루 한 번 점검합니다. 이 확장은 온비드 **홈페이지**(https://www.onbid.co.kr/)를 **매시간** 외부 이용자 관점으로 점검해(접속 → HTTP → 내용 → 기능(파일 서버) → 신선도), 상태가 바뀌면 **텔레그램으로 알리고**, 기존 이상징후 흐름(배정·조치·이력)에 그대로 올립니다. 점검 프로그램 자체가 멈추면 그것도 알립니다. 새 "홈페이지 모니터링" 화면과 대시보드 카드, 일일 점검보고서의 홈페이지 절을 추가합니다.

범위 밖(PRD §2): 온비드 내부 서버 지표, 로그인·쓰기 동작 점검, 여러 지점 관측, 기존 OpenAPI 일일 점검 주기 변경, 헤드리스 브라우저(조사 결과 불필요).

## 2. 기존 코드에서 확인한 사실

PRD §0 지침("구현 전에 기존 패턴을 먼저 읽는다")의 결과입니다. 아래 계획의 근거입니다.

| PRD가 말한 것 | 실제 코드의 모습 | 계획에 주는 영향 |
|---|---|---|
| "등록부(`targets` 테이블)" | 등록부는 **파일**(`data/registry/api-registry.json`, Zod 검증, `lib/registry`)입니다. `targets` 테이블은 없습니다. | 웹 등록부도 같은 방식의 **파일**로 만들고 DB에는 대상 키(문자열)만 둡니다. |
| 6가지 판정 | `lib/checks/probe/status.ts`·`classify.ts`가 `PASS_DATA·PASS_NO_DATA·DEGRADED·FAIL·UNVERIFIED·NOT_RUN`을 판정하고 `probe_results`에 저장(DB 제약도 6개 값). `probe_results`는 **추가 전용이 아닙니다**(수정·삭제 트리거 없음). | 같은 6개 값을 재사용하고 7번째 값을 만들지 않습니다(C4). 웹 판정 결과 테이블도 같은 성격(서버만 쓰기)으로 둡니다(D2). |
| 이상징후 생성·중복 제거 | `anomalies.source`는 `DEMO`/`PUBLIC`뿐이고 `rule_id`는 DB 제약의 허용 목록(15개)입니다. `(source, item_key, rule_id)`가 같은 **열린 건은 하나만**(`anomalies_one_active_per_identity`). 기록 함수 `record_detection`은 **정상 판정(dismissed) 건과 같은 근거 해시면 새 건을 만들지 않습니다.** | 규칙 ID 추가 마이그레이션 1개. 오탐 종결이 실제 장애를 숨기지 않도록 사건마다 다른 근거 해시를 씁니다(C15). |
| 이상징후 이력 | `anomaly_events`는 수정·삭제 금지 트리거가 있고 `event_type` CHECK·`actor_matches_event`·`values_check`가 종류별로 제한합니다. 시스템 사건은 `created`/`detected_again`뿐입니다. | "복구 확인됨" 사건을 남기려면 제약 3개와 DB 함수를 바꿔야 합니다(W14). |
| 스케줄러 | `scripts/setup-cron.mjs`가 `pg_cron`+`pg_net`으로 작업 2개를 만듭니다(점검 08:00 → 앱 경로 POST, 누락 감지 08:30 → DB 함수 직접 호출). 비밀은 Vault. `pg_cron`은 **UTC**. 출력 가림(`mask`)은 `CRON_SECRET`과 앱 주소만, `--remove`는 작업 2개만 해제. | Q8 답: UTC. 매시 `:07`은 UTC·KST 같음. **스크립트의 가림·해제 범위를 일반화해야 합니다**(W08). |
| 08:30 실행 확인 | `public.mark_schedule_missed()`가 `check_runs`의 "오늘 예약 실행"을 보고 **`run_logs`에 기록만** 합니다(외부 알림 없음). | 웹 기록이 같은 테이블에 들어가면 API 누락을 못 잡습니다(C3). "같은 방식"은 구조만 같고 **알림 발송은 새로 만듭니다**(W16). |
| 동시 실행 방지 | `check_runs_only_one_running`: **전체 `running` 1개**. `start_check_run`이 120초 지난 멈춘 실행을 정리합니다. | 웹 전용 실행 테이블과 같은 방식의 시작 함수가 필요합니다(W04). |
| 설정값 | DB `settings`(16개 키, 소문자 snake_case) + `lib/settings/schema.ts`(Zod) + DB 함수 범위 검사 + `settings-drift.test.ts`. **필수 키가 없거나 잘못되면 전체 `SettingsError`로 점검이 멈춥니다.** 선택 키 목록(`OPTIONAL_SETTING_KEYS`)이 있습니다. | 웹 키가 잘못돼도 API 점검이 멈추지 않게 **웹 전용 설정 읽기**를 따로 둡니다(§4.4). |
| 호출·시간 | 점검 경로 `maxDuration` 90초, 설정 `run_time_limit_seconds` 운영 80초(API 점검용). 지역 설정(`vercel.json`·`preferredRegion`)은 **없습니다**. | 웹 전용 시간 예산 설정과 서울 리전 설정을 새로 만듭니다(C10, W00-1). |
| 이상징후 화면 경로 | 이상징후 상세는 `/anomalies/[id]`입니다. | PRD 초안의 `/incidents/…` 링크를 `/anomalies/{id}`로 바로잡았습니다. |
| 의존 라이브러리 | `next`, `react`, `zod`, `@supabase/*`만 있습니다. | DNS·TLS·HTTP는 Node 내장(`dns`, `tls`, `fetch`)으로 가능해 **새 라이브러리가 필요 없습니다.** |
| 기능 원칙 | 모든 기능은 DEMO만으로 동작, 쓰기 요청 금지, 이력은 추가 전용, 비밀은 서버에만. 새 테이블에도 RLS 가드 시험(`00_rls_guard`: 쓰기 정책 없음)이 적용됩니다. | 웹 점검은 DEMO 출처가 없어 예외로 문서화하고 시험은 **목 서버**로 합니다(C13). 쓰기는 정책이 아니라 DB 함수로 합니다. |

### 4.3 판정·알림 흐름 (PRD §5·§6 요약)

1. 매시 `:07` `pg_cron` → `/api/cron/web-check` → `main.do`를 L1→L2→L3로 점검(앞 층이 실패하면 뒤 층은 하지 않음), 진입 스텁·대기열은 **보조 확인**.
2. 대표 판정 = 대표 판정에 포함되는 프로브(L1 인증서 임박 제외, L2, L3, M3의 L4)의 가장 나쁜 판정(실패 > 저하 > 검증 불가 > 미점검 > 정상(무데이터) > 정상(데이터)). **인증서 임박과 보조 확인은 별도 알림**.
3. 대표가 `실패`이고 열린 사건이 없으면 `web_retry_queue`에 재확인 예약. 재확인 결과별 처리는 PRD FR-4 표(실패→확정, 정상→일시 실패, 저하·검증 불가→해당 규칙). 복구는 비대칭(정상 1회로 복구).
4. 알림은 PRD FR-6 **전환표**대로(장애, 성능 저하, 지속(마지막 알림 후 ≥3시간), 복구, 인증서 하루 1회, 보조 이상 3회 연속, 점검 불가 3회 연속, 미등록 점검, 모니터 정지·재개), 멱등 키는 사건 종류별.
5. 확정 실패/저하 지속 시 `WEB_AVAILABILITY` 이상징후 생성(열린 건 있으면 발생 기록만 추가, 근거 해시에 사건 시작 시각). 복구해도 자동 종결하지 않고 이력에 `recovered` 사건.
6. 계획 점검 창 안의 결과는 `planned_maintenance=true`로 표시해 알림·가용률·이상징후에서 제외. 창 밖에서 점검 문구가 감지되면 장애 알림 대신 미등록 점검 알림 1회(이상징후 없음, 가용률 분모 제외).
7. 수동 점검은 기록만 하고 상태·사건·알림·재확인을 바꾸지 않음.
8. 하루 알림 상한(기본 12건/대상) 초과 시 이후는 기록만 + 억제 알림 1건(모니터 정지는 상한 밖). `web_monitor_enabled=false`면 전부 멈춤.

## 6. 시험 전략

- **단위**: 판정·상태 전환·메시지·멱등 키는 순수 함수로 만들어 경계값(한 칸 안·밖)을 시험하고, 네트워크·시각은 주입합니다.
- **목 서버**: 로컬 HTTP(S) 서버로 PRD §11 시나리오(503, 타임아웃, 점검 문구, 표식 누락, 차단 페이지, 리다이렉트 루프, 스텁 이동 코드 소실, 허용 밖 이동)를 재현합니다. 인증서는 만료일 + 고정 시각 주입으로 계산을 시험하고 TLS 연결 자체는 로컬 HTTPS 목 서버 1~2건만 확인합니다(새 라이브러리 없음).
- **DB(pgTAP)**: 새 테이블마다 RLS(비로그인·일반 로그인·서버 역할), 쓰기 정책 없음, 추가 전용 대상(알림 키·시도), 제약(`running` 1개, 창 종료>시작), 함수 권한(감시·삭제·창 등록은 지정한 역할만), 경계(129/130분). **시험 데이터는 `begin…rollback` 안에서만** 만듭니다.
- **시험 데이터 전략(운영 DB 공유)**: 화면 시험·`check:db`는 연결된 운영 DB를 씁니다. 홈페이지 화면 시험은 **목 저장소**를 쓰거나, 표식이 붙은 시험 대상 키를 쓰고 화면 목록에서 제외합니다. 라이브 DB 시험은 만든 줄만 지웁니다(웹 판정 결과 테이블은 추가 전용이 아니라서 가능).
- **화면(Playwright)**: `/web` 조회, 계획 점검 창(팀장만), 수동 점검, 알림 실패 표시, 홈페이지 카드(모바일). 시험 전용 계정 그대로 사용합니다.
- **회귀**: 기존 단위·pgTAP·화면 시험이 계속 통과해야 합니다. 특히 `mark_schedule_missed`, `check_runs`, `settings` 로더, `00_rls_guard`.
- **운영 확인(자동 시험으로 못 하는 것)**: 서울 리전 접속, 연속 24회 실행, 실제 텔레그램 1건 수신, 매시간 작업 정지 시 정지 알림, `pg_net` 기록의 토큰 잔존 여부. 결과를 문서에 기록합니다.

## 7. 보안·운영

- 텔레그램 토큰은 `NEXT_PUBLIC_`을 붙이지 않고 브라우저 코드·로그·DB 평문·커밋에 넣지 않습니다. DB 쪽 감시용은 Vault, 앱 쪽 알림용은 Vercel 환경변수(Secret)입니다. **크론 등록 스크립트의 미리 보기 출력에 모든 비밀값이 가려지게** 합니다(W08). 알림 메시지에는 비밀값·요청 헤더·개인정보를 넣지 않습니다.
- 온비드에는 **읽기 전용 GET만** 보냅니다(코드에서 메서드 고정 + 시험). 요청마다 https와 허용 호스트(`www.onbid.co.kr`, `wait.onbid.co.kr`)만 허용합니다.
- **요청 수**: 대상 1개·시간당 `main.do` 1, 진입 스텁 1, 대기열 설정 1, JS 번들 1~2, (M3) 이미지 1 = **약 5~7개**, 확인 재시도가 있으면 한 번 더. 동시 요청 없음, 요청 사이 약 0.5초, 웹 전용 시간 예산 60초. 승인(C2) 때 말씀드린 "2~3회"보다 늘어난 값입니다.
- 고정 User-Agent `OnBidOpsRadar-Monitor/1.0`(연락처·개인정보 없음). 화면·보고서·알림에 "단일 지점, 1시간 간격 외부 관측이며 간격 사이의 짧은 장애는 탐지하지 못한다"고 적습니다.
- 끄기·롤백: `web_monitor_enabled=false`와 `setup-cron --remove-web`으로 즉시 멈출 수 있고, 새 DB 객체는 마이그레이션 파일로만 만듭니다.
- 토큰 만료 관리: Vercel·Supabase·GitHub 토큰 점검 일정에 텔레그램 봇 토큰 점검(유출 시 즉시 교체, **Vercel과 Vault 두 곳**)을 추가합니다.

## 8. 위험과 완화

| 위험 | 완화 |
|---|---|
| 오탐으로 인한 알림 피로 | 확인 재시도, 상태 전환 알림만, 4xx는 검증 불가로 분리, 인증서·보조 프로브는 별도 알림, 하루 알림 상한, **1주 관찰을 건너뛰지 않음** |
| 알림 폭주(상태 진동) | 하루 상한(기본 12건/대상)과 억제 알림 1건, 복구는 정상 1회 판정이므로 진동은 상한으로 막음 |
| 해외 IP·WAF 차단 | 서울 리전 + W00-1에서 먼저 확인, 차단 문구는 검증 불가, 첫 주 사무실 브라우저 대조 |
| 이동 스텁만 보고 정상 오판 | 판정은 `main.do` 기준, 스텁은 이동 코드 확인 |
| 웹 점검이 기존 API 점검을 방해 | 별도 테이블·별도 `running` 제약(C3), 웹 전용 설정 읽기, 회귀 시험 |
| 웹 설정 오류가 API 점검을 멈춤 | 웹 전용 설정 읽기, 웹 키는 기존 필수 키 목록에 넣지 않음 |
| 알림 도구 변경(기관 지침) | `Notifier` 구현체만 교체 |
| 실행 시간 초과 | 웹 전용 시간 예산, 요청 타임아웃은 남은 예산 이하, 재시도는 별도 실행 |
| 분 단위 스케줄러로 재시도 지연 | 문서화(90~150초), 알림에 실제 재확인 시각 |
| 텔레그램 토큰이 `pg_net` 기록에 남음 | W16에서 확인, 남으면 즉시 지우거나 방식 변경 |
| 비공개·변경되는 파일 서버 주소(L4) | 검증 불가 처리·등록부 갱신 표시 |
