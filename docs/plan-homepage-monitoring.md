## 1. 무엇을 만드는가 (한 문단)

지금은 온비드 **OpenAPI**만 하루 한 번 점검합니다. 이 확장은 온비드 **홈페이지**(https://www.onbid.co.kr/)를 **매시간** 외부 이용자 관점으로 점검해(접속 → HTTP → 내용 → 기능 → 신선도), 상태가 바뀌면 **텔레그램으로 알리고**, 기존 이상징후 흐름(배정·조치·이력)에 그대로 올립니다. 점검 프로그램 자체가 멈추면 그것도 알립니다. 대시보드에는 홈페이지 카드를, 일일 점검보고서에는 홈페이지 절을 추가합니다.

범위 밖(PRD §2): 온비드 내부 서버 지표, 로그인·쓰기 동작 점검, 여러 지점 관측, 기존 OpenAPI 일일 점검 주기 변경.

## 2. 기존 코드에서 확인한 사실 (PRD §0 지침의 "먼저 읽기" 결과)

PRD는 구현 전에 기존 패턴을 찾아 읽으라고 했습니다. 읽은 결과입니다. 이 사실들이 아래 계획의 근거입니다.

| PRD가 말한 것 | 실제 코드의 모습 | 계획에 주는 영향 |
|---|---|---|
| "등록부(`targets` 테이블)" | 등록부는 DB 테이블이 **아니라 파일**입니다: `data/registry/api-registry.json`(Zod로 검증, `lib/registry`). `targets` 테이블은 없습니다. | 웹 대상 등록부도 같은 방식의 **파일**로 만들고, DB에는 대상 키(문자열)만 둡니다. |
| 6가지 판정 | `lib/checks/probe/status.ts`·`classify.ts`가 `PASS_DATA·PASS_NO_DATA·DEGRADED·FAIL·UNVERIFIED·NOT_RUN`을 판정하고 `probe_results`에 저장합니다. DB에도 이 6개 값의 제약이 있습니다. | 같은 6개 값과 같은 사전(`describeProbe` 등)을 재사용합니다. 7번째 값을 만들지 않습니다(§3 C4). |
| 이상징후 생성·중복 제거 | `anomalies`는 `source`가 `DEMO`/`PUBLIC`뿐이고, `rule_id`는 DB 제약으로 허용 목록(15개)이 있습니다. `(source, item_key, rule_id)`가 같은 **열린 건은 하나만** 있도록 유니크 인덱스(`anomalies_one_active_per_identity`)가 막습니다. | 새 규칙 ID를 마이그레이션으로 추가하면 중복 제거는 기존 인덱스가 그대로 해 줍니다. |
| 스케줄러 | `scripts/setup-cron.mjs`가 Supabase `pg_cron` + `pg_net`으로 작업 2개를 만듭니다(점검 08:00 → 앱 경로 POST, 누락 감지 08:30 → DB 함수 직접 호출). 비밀은 Supabase **Vault**에 있습니다. `pg_cron`은 **UTC**로 해석합니다(KST 08:00 = UTC 23:00). | PRD의 Q8 답: UTC입니다. 매시 `:07`은 한국이 UTC+9(정시 차이)라서 **UTC·KST 모두 `7 * * * *`로 같습니다.** |
| 08:30 실행 확인 | `public.mark_schedule_missed()` DB 함수가 `check_runs`에서 "오늘 예약 실행"이 있는지 봅니다. | 이 함수는 **모든 예약 실행**을 셉니다. 웹 점검 기록이 같은 테이블에 들어가면 API 누락을 못 잡습니다(§3 C3). |
| 동시 실행 방지 | `check_runs_only_one_running` 유니크 인덱스: **전체에서 `running`은 1개**뿐입니다. | 웹 점검을 같은 테이블에 넣으면 매시간 실행이 API 점검과 서로 차단합니다(§3 C3). |
| 설정값 한곳 관리 | DB `settings` 테이블(16개 키, 소문자 `snake_case`) + `lib/settings/schema.ts`(Zod) + DB 함수의 범위 검사 + `settings-drift.test.ts`. **키를 추가하려면 마이그레이션이 필요**합니다. | PRD의 대문자 키를 우리 이름으로 옮기고, 키마다 마이그레이션·Zod·드리프트 시험을 함께 고칩니다(§4.4). |
| 호출·시간 | 점검 경로 `maxDuration`은 90초, 실행시간 제한 설정은 80초. 점검 함수 지역 설정(`vercel.json`·`preferredRegion`)은 **없습니다**. | 서울 리전(`icn1`) 고정은 새로 설정해야 합니다(§3 C10). |
| 의존 라이브러리 | `next`, `react`, `zod`, `@supabase/*`만 있습니다. | DNS·TLS·HTTP는 Node 내장(`dns`, `tls`, `fetch`)으로 가능해서 **새 라이브러리가 필요 없습니다.** |
| 기능 원칙 | 모든 기능은 DEMO만으로 동작, 쓰기 요청 금지, 변경 이력은 추가 전용, 비밀은 서버에만. | 웹 점검은 DEMO 출처가 없습니다. 예외를 문서화하고 시험은 **목(mock) 서버**로 합니다(§3 C13). |

## 4. 설계 개요 (권장안 기준)

### 4.1 폴더·파일 (제안)

```
data/registry/web-targets.json         웹 대상 등록부(Zod 검증). onbid-home 1개로 시작
lib/web-monitor/
  schema.ts                            등록부·설정 Zod 스키마
  probes/connect.ts                    L1 DNS·TCP·TLS·인증서 남은 일수 (Node tls/dns)
  probes/http.ts                       L2 상태 코드·응답 시간·리다이렉트 추적(수동, 최대 10회)
  probes/content.ts                    L3 표식·점검 문구·크기 하한·JS 번들 확인
  classify.ts                          프로브 판정(결정적 순수 함수) + 대표 판정
  runner.ts                            대상 1개 점검 실행(프로브 호출, 격리, 시간 한도)
  state.ts                             상태 전환·연속 횟수·중복 억제(순수 함수)
  maintenance.ts                       계획 점검 창 판정
  notify/types.ts                      Notifier 인터페이스
  notify/telegram.ts                   TelegramNotifier(재시도 3회, 멱등 키)
  notify/messages.ts                   메시지 문구(KST, 지속 시간 오차 표기)
app/api/cron/web-check/route.ts        매시간 점검 입구(CRON_SECRET 인증, 기존 경로와 같은 방식)
app/api/cron/web-retry/route.ts        재확인 입구(매분 작업이 부름)
supabase/migrations/…                  테이블·함수·제약(§4.2)
scripts/setup-cron.mjs                 작업 추가: 매시 점검, 매분 재확인, 자체 감시
```

### 4.2 데이터 모델 (PRD §7을 기존 규칙에 맞춘 안)

| 테이블/함수 | 하는 일 | 비고 |
|---|---|---|
| `web_check_runs` | 웹 점검 1회(상태, 시작·종료, 트리거) | `running` 1개 제약은 **웹 전용**. 기존 `check_runs`와 완전 분리(C3) |

### 4.3 판정·알림 흐름 (PRD §5·§6 요약)

1. 매시 `:07` `pg_cron` → `/api/cron/web-check`(CRON_SECRET 인증) → 대상마다 L1→L2→L3 순서로 점검(앞 층이 실패하면 뒤 층은 하지 않음).
2. 대표 판정 = 가장 나쁜 프로브 판정(우선순위: 실패 > 저하 > 검증 불가 > 미점검 > 정상(무데이터) > 정상(데이터)).
3. 대표가 `실패`이면 `web_retry_queue`에 재확인을 예약. 재확인도 `실패`일 때만 **확정 실패**로 기록(정상이면 `일시 실패(flap)`로 기록만, 알림·이상징후 없음).
4. 상태가 바뀔 때만 알림: 확정 실패 → 장애, 저하 2회 연속 → 성능 저하, 실패/저하 → 복구, 지속 3시간마다 재알림, 인증서 14일 이내 하루 1회, 검증 불가·미점검 3회 연속 → 점검 불가 지속, 미등록 점검 문구 → 1회.
5. 확정 실패/저하 지속 시 `WEB_AVAILABILITY` 이상징후 생성(열린 건이 있으면 발생 기록만 추가). 복구해도 자동 종결하지 않음(C9).
6. 계획 점검 창 안의 실패는 판정은 남기고 `planned_maintenance`로 표시해 알림·가용률·이상징후에서 제외.

## 6. 시험 전략

- **단위**: 판정·상태 전환·메시지·멱등 키는 모두 순수 함수로 만들고 경계값(한 칸 안·밖)을 시험합니다. 네트워크·시각은 주입합니다.
- **목 서버**: 로컬 HTTP(S) 서버로 PRD §11의 시나리오(503, 타임아웃, 점검 문구, 표식 누락, 차단 페이지, 리다이렉트 루프)를 재현합니다. 인증서 만료는 실제 TLS 대신 **인증서 만료일과 고정 시각**을 주입해 계산을 시험하고, TLS 연결 자체는 로컬 HTTPS 목 서버(시험용 인증서 파일)로 1~2건만 확인합니다. 새 라이브러리는 쓰지 않습니다.
- **DB(pgTAP)**: 새 테이블마다 RLS(비로그인·일반 로그인·서버 역할), 추가 전용(수정·삭제 거부), 제약(`running` 1개, 창 종료>시작), 함수 권한(감시 함수는 서버만 실행)을 시험합니다.
- **화면(Playwright)**: 계획 점검 창(팀장만), 수동 점검 버튼, 알림 실패 표시, 홈페이지 카드(모바일 포함). 시험 전용 계정을 그대로 사용합니다.
- **회귀**: 기존 745개 단위, 467개 pgTAP, 51개 화면 시험이 계속 통과해야 합니다. 특히 `mark_schedule_missed`와 `check_runs`는 바뀌지 않아야 합니다.
- **운영 확인(자동 시험으로 못 하는 것)**: 연속 24회 실행, 실제 텔레그램 1건 수신, 매시간 작업 정지 시 130분 안에 감시 알림. 결과를 문서에 기록합니다.

## 7. 보안·운영

- 텔레그램 토큰은 `NEXT_PUBLIC_`을 붙이지 않고 브라우저 코드·로그·DB 평문·커밋에 넣지 않습니다. DB 쪽 감시용은 Vault, 앱 쪽 알림용은 Vercel 환경변수(Secret)로만 둡니다. 알림 메시지에는 비밀값·요청 헤더·개인정보를 넣지 않습니다.
- 온비드에는 **읽기 전용 GET만** 보냅니다. 로그인·폼 제출·쓰기 요청 금지(코드에서 메서드를 GET으로 고정하고 시험).
- 요청 수: 대상당 시간당 L1~L3 2~3개(+확인 재시도), 동시 요청 없음, 요청 사이 간격 유지. 고정 User-Agent(`OnBidOpsRadar-Monitor/1.0`).
- 이 서비스의 정체(외부 합성 점검)에 맞게 화면·보고서·알림에 "단일 지점, 1시간 간격 외부 관측이며 간격 사이의 짧은 장애는 탐지하지 못한다"고 적습니다.
- 토큰 만료 관리: 기존 Vercel·Supabase·GitHub 토큰 점검 일정에 텔레그램 봇 토큰 점검을 추가합니다(봇 토큰 자체는 기본적으로 만료되지 않지만 유출 시 즉시 교체).

## 8. 위험과 완화

| 위험 | 완화 |
|---|---|
| 오탐으로 인한 알림 피로 | 확인 재시도, 상태 전환 알림만, 4xx는 검증 불가로 분리, **1주 관찰 기간을 건너뛰지 않음** |
| 해외 IP·WAF 차단 | 서울 리전, 차단 문구는 검증 불가, 첫 주 사무실 브라우저 대조 |
| 홈페이지가 JS로 그려서 HTTP 200만으로는 정상 판단 불가(PRD §1) | L3 표식·JS 번들 확인으로 "껍데기만 뜨는 장애"를 잡고, M0에서 실제 HTML로 표식을 확정 |
| 비공개 L4 요청의 변경 | 실패가 아니라 검증 불가, 등록부 갱신 필요 표시 |
| 웹 점검이 기존 API 점검을 방해 | 별도 테이블·별도 `running` 제약(C3), 기존 시험 회귀로 확인 |
| 알림 도구 변경(기관 지침) | `Notifier` 인터페이스로 구현체만 교체 |
| 실행 시간 초과 | 대상별 타임아웃 합계 검증(설정 간 관계 시험), 재시도는 별도 실행 |
| 분 단위 스케줄러로 인한 재시도 지연 오차 | 문서화(90~150초), 알림 메시지에 재확인 시각을 실제 값으로 표기 |

## 9. 완료 정의와 문서 갱신

- 각 마일스톤의 수용 기준(§5)을 증거(시험 결과·운영 기록)와 함께 충족.
