## 1. 한 줄 요약

온비드 OpenAPI를 **외부 이용자 관점으로 합성 점검**하고, 이상징후 탐지 → 담당자 확인·조치 → 일일 보고서까지 이어 주는 내부 업무용 웹서비스(교육용 PoC)를 PRD v2.0의 R01~R08 단위까지 구현했다. 설계 대비 일치율은 **87.5%**(90% 미만)이며, 남은 차이는 대부분 **실제 환경 확인·사용자 승인**이 있어야 메워진다.

> 이 서비스의 숫자는 "우리 점검 요청에 관측된 결과"일 뿐 온비드 서버 전체의 가용성·호출량·원천 데이터 건수가 아니다. 화면·보고서에도 항상 그렇게 적는다.

## 4. 설계 대비 Gap

[docs/gap-analysis.md](gap-analysis.md) 기준 **일치율 87.5%** = (구현 36 + 0.5 × 부분 구현 5) ÷ (46 − 의도적 보류 2). 도메인 원칙(이상징후 표현, DEMO·PUBLIC 분리, 미점검·검증 불가를 정상으로 세지 않음 등) 위반은 없었다.

남은 부분 구현 5개:
1. **26종 중 실제 점검 가능한 오퍼레이션은 28개 중 23개** — 23개 모두 2026-11-03 사용자 실호출 확인 완료(PASS_DATA). 나머지 5개(019·021~024)는 점검 입력의 근거가 없어 `UNVERIFIED(NO_VALID_INPUT)`로 둔다.
2. 서비스 단위 배치 **실행기** — 계획과 격리까지만 있다.
3. `DQ_LIST_DETAIL_REF`의 상세 0건 **재조회** — 판정 보류 메모만 남긴다.
4. `DQ_CROSS_API_REF` — 공고 목록(015) → 공고 상세(016)를 공식 관계로 연결했다. 016은 2026-11-03 사용자가 `npm run test:public-probes`로 실호출을 확인했다(PASS_DATA, 필수 항목 누락 0, 식별키 일치). 관계가 없거나 부모에서 식별키를 얻지 못하면 적용 제외로 남긴다.
5. 등록부 값 채움(무데이터 정책·점검 주기·Probe 방식) — 사용자 확인이 필요한 항목.

## 5. 알려진 한계와 주의점

- **PUBLIC 키는 2026-11-03에 사용자가 Vercel Production에 등록했다**(승인 확인은 사용자 책임, PRD 6-4). 같은 날 배포 사이트에서 PUBLIC 수동 점검을 실행해 성공했다(호출 26회, 12개 서비스 정상). 예약 점검(Cron)은 아직 등록하지 않아 자동으로는 돌지 않는다.
- **예약 점검(Cron)은 2026-11-03에 등록했다.** Vercel `CRON_SECRET` 등록·재배포 후 `setup:cron --apply`로 작업 2개(KST 09:00 점검, 09:30 누락 감지)를 만들었고, 예약 점검 출처(`scheduled_source`)는 PUBLIC으로 바꿨다. 같은 요청을 한 번 보내 확인했다(응답 200, 실행 #682 PUBLIC 예약 성공, 호출 28회). 첫 자동 실행은 다음 날 KST 09:00이다. 해제는 `npm run setup:cron -- --remove --apply`.
- 서비스별 호출 예산·초당 제한은 아직 없다. 현재는 전체 일일 예산(900회)과 실행당 호출 상한(기본 60회)만 있다.
- 호출 상한은 점검 오퍼레이션이 늘 때마다 올려야 한다. 상세 표본 수를 별도 설정으로 분리하면 해결된다(미구현).
- 개인 자료 `docs/온비드 OPEN API.md`가 로컬 커밋에 잘못 들어갔던 적이 있어, 2026-11-03 `main`의 로컬 커밋 36개에서 이력을 다시 써서 완전히 제거했다(트리는 동일, `.gitignore`에 등록). 원격에는 올라간 적이 없다. 되돌릴 수 있게 남긴 로컬 태그 `backup-pre-rewrite-main`에는 아직 들어 있으므로, 확인 후 태그를 지우고 `git reflog expire --expire=now --all && git gc --prune=now`로 완전히 정리한다(푸시 전에는 `--tags`·`--all`로 올리지 않는다).
- 사용자 PC의 수집 스크립트 폴더에는 서비스키가 평문으로 들어 있다. 일부가 한 번 도구 출력에 보인 적이 있어 **재발급을 권한다.**
