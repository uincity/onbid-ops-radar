# OnBid Ops Radar (온비드 운영·품질 통합 모니터링)

온비드 공매정보의 **데이터 품질**과 **OpenAPI 운영상태**를 자동으로 점검하고, 이상징후 탐지 → 담당자 확인·조치 → 일일 점검보고서까지 지원하는 **내부 업무용 웹서비스**입니다(교육용 PoC 단계를 마치고 실제 점검 이력을 쌓는 중).
투자자에게 물건을 추천하는 서비스가 아니라, 온비드를 안정적으로 운영하도록 돕는 업무 자동화 서비스입니다.

- 기획서: [PRD.md](PRD.md) · 개발 계획: [PLAN.md](PLAN.md) · 설계: [DESIGN.md](DESIGN.md) · 작업 규칙: [CLAUDE.md](CLAUDE.md)
- 남은 작업 정리와 PoC 압축 계획: [PLAN-POC.md](PLAN-POC.md)

## 지금 어디까지 만들었나 (2026-11-04 기준)

PRD v2.0의 개발 단위 R01~R08을 모두 구현했고 운영 환경(Vercel)에 배포해 **실제 온비드 OpenAPI 점검 이력을 쌓는 단계**입니다. 다만 아래의 "아직 안 된 것"이 남아 있습니다.

| 구분 | 상태 |
|---|---|
| 로그인(이메일·비밀번호), 비로그인 차단, 팀장/운영 담당자 역할, 모든 테이블 RLS | 구현됨 |
| 실명 계정 운영: 계정 추가 명령(`add:account`), 일회용 링크로 본인이 비밀번호 설정 | 구현됨 (팀장 1·운영 담당자 1명 로그인 확인) |
| 온비드 서비스 등록부 25종·28개 오퍼레이션 (26번째 서비스는 미확정) | 구현됨 |
| API 점검 상태 6종 판정(`PASS_DATA`·`PASS_NO_DATA`·`DEGRADED`·`FAIL`·`UNVERIFIED`·`NOT_RUN`)과 DB 저장 | 구현됨 |
| 서비스 단위 배치 점검: 서비스별 하루 호출 예산·호출 간격, 한 API의 실패가 다른 API를 막지 않음 | 구현됨 |
| 실제 호출 확인: 28개 오퍼레이션 중 **27개가 정상 응답(`PASS_DATA`)**, 1개(022)는 모든 입력에서 0건이라 "정상 무데이터(`PASS_NO_DATA`)"로 처리(실데이터는 미확인) | 확인됨 (2026-11-03) |
| 데이터 품질 규칙 4개(`DQ_SCHEMA`·`DQ_REQUIRED`·`DQ_LIST_DETAIL_REF`·`DQ_CROSS_API_REF`), API 간 관계 8개 검증 | 구현됨 |
| 이상징후 목록·상세·배정·처리·이력, 대시보드(26종 가용성), 일일 점검보고서 | 구현됨 |
| **예약 점검: 매일 KST 08:00 PUBLIC 점검, 08:30 누락 감지** (Supabase Cron) | 운영 중 (2026-11-04 08:00 첫 자동 실행, 실행시간 제한 80초로 조정) |
| 수동 점검 (팀장), 점검 이력 | 구현됨 (출처는 PUBLIC) |
| 화면의 데이터 출처 표시 | PUBLIC만 표시 (DEMO 표시는 화면에서 제거) |

**검증 현황:** 단위 테스트 739개 통과, DB 보안·무결성 pgTAP 467개 통과, 화면 자동 테스트 51개 통과(4개는 데이터가 없어 건너뜀, 시험 전용 계정 사용), 린트·타입 검사·빌드 통과. 설계 대비 일치율 91.1% ([docs/gap-analysis.md](docs/gap-analysis.md)).

**아직 안 된 것 / 알아둘 점**

- 26종 중 **26번째 서비스는 어떤 것인지 미확정**입니다. 022번(공유일반재산)은 9가지 입력 모두 0건이라 사용자 결정으로 "정상 무데이터"로 처리했고, 실데이터 응답은 아직 확인하지 못했습니다. 26종 전체가 정상이라고 주장하지 않습니다.
- 지금 화면에는 실제 점검이 만든 이상징후가 아직 없습니다(PUBLIC 점검에서 이상징후가 나온 적이 없음).
- 운영 DB의 DEMO 데이터는 삭제했고(복구 불가), 코드의 DEMO 점검 기능은 서비스키·한도 문제 시 대비책과 시험용으로 남겨 두었습니다.
- 점검 서비스가 늘면 실행시간 제한(현재 80초, 점검 경로 최대 90초)에 다시 걸릴 수 있습니다.
- 자세한 내용: [docs/completion-report.md](docs/completion-report.md) · PRD 부록 F(v2.1 추가 요구사항)

이 서비스의 숫자는 "우리 점검 요청에 관측된 결과"일 뿐 온비드 서버 전체의 가용성·호출량·원천 데이터 건수가 아닙니다. 실제 개인정보와 온비드 운영시스템에는 접근하지 않습니다(읽기 전용 호출만).

## 핵심 원칙

- 탐지 결과는 "오류"가 아니라 항상 **"이상징후"** 로 표현합니다. 규칙 기반이며 LLM을 쓰지 않습니다.
- 처리상태: `open` → `investigating` → `resolved` / `dismissed` (종결 건 재개만 허용).
- 변경 이력은 **추가만** 가능합니다(수정·삭제 불가).
- 권한은 화면이 아니라 **서버와 Supabase RLS** 에서 검사합니다.

## 로컬 실행

```bash
npm install
npm run dev
```

`.env`가 필요합니다. 변수 이름 목록은 [.env.example](.env.example)에 있고, 실제 값은 저장소에 올리지 않습니다.

| 목적 | 명령 |
|---|---|
| 단위 테스트 | `npm run test:unit` |
| 화면 자동 테스트 | `npm run test:e2e` |
| DB 보안 테스트 | `npm run test:db` |

## 보안

- `.env`와 `node_modules`는 저장소에 올리지 않습니다.
- 서버 전용 키(`SUPABASE_SECRET_KEY` 등)는 브라우저 코드에서 쓰지 않습니다.
- 공개 회원가입은 없습니다. 계정은 아래 "사용자 계정 관리" 절차로만 만듭니다.

## 사용자 계정 관리

역할은 두 가지입니다. 팀장(`admin`)과 운영 담당자(`operator`). 역할은 서버 관리 절차로만 부여하며, 화면에서 계정을 만들거나 역할을 바꾸는 기능은 없습니다.

### 계정 추가

서버 전용 키(`SUPABASE_SECRET_KEY`)가 `.env`에 있는 관리자 컴퓨터에서 실행합니다.

```bash
npm run add:account -- --email 주소 --name 이름 --role admin
npm run add:account -- --email 주소 --name 이름 --role operator
```

- `--role`은 `admin`(팀장) 또는 `operator`(운영 담당자)입니다.
- 비밀번호는 아무도 모릅니다. 명령이 일회용 **비밀번호 설정 링크**를 터미널에 출력하면, 그 링크를 본인에게 전달합니다.
- 본인이 링크를 열면 `/auth/confirm`에서 확인된 뒤 `/reset-password`에서 비밀번호(12~72자)를 직접 정합니다.
- 링크는 한 번만 쓸 수 있고 일정 시간 뒤 만료됩니다. 링크는 터미널에만 출력되므로 채팅·문서·커밋에 남기지 마세요.

### 비밀번호를 잊었거나 링크가 만료됐을 때

```bash
npm run add:account -- --email 주소 --link-only
```

이미 있는 계정의 새 설정 링크만 다시 만듭니다. 이름과 역할은 바꾸지 않습니다.

### 이름·역할 바꾸기

같은 이메일로 `--name`, `--role`을 넣어 다시 실행하면 이름과 역할이 입력한 값으로 맞춰집니다.

### 사용을 그만둘 때

계정을 지우지 않고 **정지**합니다. 처리 이력과 보고서가 작성자 계정을 가리키고 있어서, 지우면 이력의 작성자를 잃습니다.

### 시연 계정 (사용 중지)

가상 시연 계정(`setup:accounts`가 만든 `DEMO_*` 2개)은 2026-11-04에 **정지**했습니다(삭제하지 않음: 보고서·이력이 이 계정을 작성자로 가리킴). 더는 쓰지 않습니다.

### 시험 전용 계정

화면 자동 테스트(`npm run test:e2e`)와 `npm run check:accounts`는 `e2e-admin@example.com`(팀장)·`e2e-operator@example.com`(운영 담당자)를 씁니다. 실행할 때 계정을 준비하고 비밀번호를 새로 무작위로 만들어 환경변수에만 두며(파일·`.env`에 저장하지 않음), 끝나면 정지합니다. 실사용 계정과 무관한 가상 이메일이며, 이 계정이 만든 처리 이력이 남을 수 있어 삭제하지는 않습니다.

### 관련 설정

- Supabase Auth의 "Allow new users to sign up"은 꺼 둡니다(공개 회원가입 금지). 대시보드에서 직접 바꾸며, `npm run check:accounts`가 켜져 있으면 알려 줍니다.
- 비밀번호 설정 링크의 유효시간은 Supabase 설정을 따릅니다. 만료가 너무 짧거나 길면 Supabase 대시보드의 Auth 설정에서 조정합니다.
